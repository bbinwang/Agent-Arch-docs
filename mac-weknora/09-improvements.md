# 第 9 章 改进建议、风险点与未来规划

> 基于对 WeKnora 全量代码的深入分析，本章从架构、性能、安全、可维护性四个维度给出客观的优缺点评估，并列出技术债清单与优先级。

---

## 9.1 架构优点

### 9.1.1 模块化设计（★★★★★）

**优点**：所有外部依赖（LLM、向量库、存储、IM、搜索引擎）均抽象为接口，实现可热插拔。

**证据**：
- `models/provider/` 29 个 Provider 统一 `chat.Chat` 接口
- `infrastructure/web_search/` 9 个引擎统一 `WebSearchProvider` 接口
- `internal/im/` 9 个适配器统一 `im.Adapter` 接口
- `service/file/` 10 个存储后端统一 `interfaces.FileService`

**价值**：企业可在不修改代码的情况下切换底层基础设施，满足数据主权和合规要求。

### 9.1.2 分层清晰（★★★★★）

**优点**：Handler → Service → Repository → Models 严格分层，依赖方向单向。

**证据**：
- Handler 仅做参数绑定 + Service 调用 + 响应渲染
- Service 编排业务逻辑，不直接操作 DB
- Repository 封装所有数据库访问
- 接口定义在 `types/interfaces/`，实现可替换

### 9.1.3 多租户安全（★★★★★）

**优点**：4 级 RBAC + 资源所有权 + KB 访问控制 + 审计日志，企业级安全。

**证据**：
- `middleware/rbac.go` 双轴授权（角色 + 所有权）
- `middleware/kb_access.go` 3 步 KB 访问检查（自有/组织共享/Agent 共享）
- 三级审计（操作审计/知识库活动/系统审计）
- AES-256-GCM 静态加密 + gRPC TLS + Redis TLS

### 9.1.4 双部署模式（★★★★☆）

**优点**：Lite 模式（无 Redis，单进程）和分布式模式（Redis/asynq）统一代码库。

**价值**：开发测试用 Lite，生产部署用分布式，降低运维复杂度。

### 9.1.5 可观测性（★★★★☆）

**优点**：Langfuse 全链路追踪 + 5 阶段文档解析 Trace + 运行时任务仪表盘。

**价值**：Agent 推理过程完全透明，便于调试和优化。

## 9.2 当前架构的瓶颈与缺点

### 9.2.1 代码规模过大（★★★☆☆）

**问题**：
- `internal/application/service/knowledge_process.go` 单文件 ~3450 行
- `internal/application/service/knowledge_faq_import.go` ~106KB
- `internal/application/service/wiki_ingest.go` ~117KB
- `internal/router/router.go` 2391 行

**影响**：
- 单文件过大导致 Code Review 困难
- 多人协作易冲突
- 编译时间较长

**建议**：
- 将 `knowledge_process.go` 拆分为 `chunking.go`、`embedding.go`、`indexing.go`、`summary.go`、`question_generation.go`
- 将 `wiki_ingest.go` 拆分为 `ingest_orchestrator.go`、`ingest_pending_ops.go`、`ingest_finalize.go`
- 将 `router.go` 按业务域拆分为多个注册函数文件

### 9.2.2 Handler 层臃肿（★★★☆☆）

**问题**：
- `handler/session/qa.go` 的 `parseQARequest` 函数过长（~300 行）
- 部分 Handler 包含大量辅助函数和 DTO 定义
- Handler 与 Service 边界模糊（部分业务逻辑在 Handler 中）

**建议**：
- 将请求解析逻辑抽取到独立的 `request.go` 文件
- DTO 统一放到 `types/` 或独立 `dto/` 包
- 严格遵循"Handler 只做绑定和渲染"原则

### 9.2.3 错误处理不一致（★★☆☆☆）

**问题**：
- 部分使用自定义 `errors.AppError`
- 部分使用标准 `errors.New`
- 部分使用 `fmt.Errorf` + `%w`
- 错误码定义分散

**建议**：
- 统一使用 `errors.AppError` + 错误码注册表
- 建立错误码文档（错误码 → HTTP 状态码 → 处理建议）

### 9.2.4 测试覆盖不均衡（★★★☆☆）

**问题**：
- 核心模块（Agent 引擎、RAG 管道）测试较完善
- 部分 Handler 缺少测试
- E2E 测试覆盖不足
- 缺少性能基准测试

**建议**：
- 补充 Handler 层表驱动测试
- 添加 API 集成测试（httptest）
- 添加性能基准测试（检索延迟、并发问答）

### 9.2.5 配置管理复杂（★★☆☆☆）

**问题**：
- `.env.example` 37KB，~200 个环境变量
- 配置验证分散在多处
- 缺少配置文档

**建议**：
- 按功能分组环境变量（DB/Cache/Storage/LLM/Security）
- 提供配置生成器（交互式 CLI）
- 添加配置变更影响说明

## 9.3 性能优化建议

### 9.3.1 数据库层

| 热点 | 影响 | 优化建议 | 优先级 |
|------|------|---------|--------|
| 知识检索并发嵌入 | 嵌入 API 调用次数多 | 查询级嵌入缓存（LRU）| P0 |
| 会话消息加载 | 大表全量扫描 | 分页 + 覆盖索引 | P1 |
| 审计日志写入 | 高频写入 | 异步批量写入 | P1 |
| Wiki 页面查询 | 大文本字段 | 分离内容表 | P2 |
| doc_count 反规范化 | 计数不准确风险 | 定期校准任务 | P2 |

### 9.3.2 缓存策略

| 缓存目标 | 当前状态 | 建议 | 预期收益 |
|---------|---------|------|---------|
| 嵌入向量 | 无缓存 | LRU 缓存（查询 → 向量）| 减少 50% 嵌入 API 调用 |
| LLM 响应 | Prompt Cache | 扩展至语义缓存 | 减少 30% Token 消耗 |
| 知识库元数据 | 每次 DB 查询 | Redis 缓存（TTL 5m）| 减少 DB 查询 |
| 会话上下文 | 每次加载 | 热会话缓存 | 减少延迟 |
| 系统设置 | 已缓存（Redis Pub/Sub）| 保持 | - |

### 9.3.3 并发优化

| 热点 | 当前状态 | 建议 | 优先级 |
|------|---------|------|--------|
| 文档解析 | 串行分块 → 嵌入 | 流水线并行（分块‖嵌入）| P0 |
| Agent 工具调用 | 已支持并行 | 增加批处理模式 | P1 |
| SSE 事件推送 | 单连接 | 连接池 + 批量推送 | P2 |
| 向量索引 | 批量索引 | 异步索引 + 增量更新 | P1 |

### 9.3.4 LLM 成本优化

| 策略 | 实施方式 | 预期节省 |
|------|---------|---------|
| 查询缓存 | 语义相似查询返回缓存结果 | 20-40% |
| Prompt 压缩 | 动态裁剪历史上下文 | 15-30% |
| 模型路由 | 简单查询用小模型，复杂用大模型 | 30-50% |
| Token 预算 | 按会话/用户设置 Token 上限 | 防止滥用 |
| 批处理 | 多个查询批量调用 LLM | 10-20% |

## 9.4 安全加固建议

### 9.4.1 高优先级

| 风险 | 当前措施 | 加固建议 |
|------|---------|---------|
| SSRF | 基础校验 | 增加 DNS rebinding 防护 + 响应头校验 |
| 依赖漏洞 | Dependabot | 增加 SCA 扫描（Snyk/Trivy）|
| 密钥管理 | 环境变量 | 支持 KMS/Vault 集成 |
| API Key 泄露 | SHA-256 存储 | 增加 Key 轮换机制 |

### 9.4.2 中优先级

| 风险 | 当前措施 | 加固建议 |
|------|---------|---------|
| Prompt 注入 | 基础消毒 | 增加 Prompt 注入检测 |
| 越权访问 | RBAC | 增加资源级 ABAC |
| 日志泄露 | 脱敏 | 增加日志完整性校验 |
| 会话劫持 | JWT | 增加设备指纹绑定 |

### 9.4.3 合规建议

| 合规项 | 建议 |
|--------|------|
| GDPR | 数据导出/删除 API、数据处理记录 |
| SOC 2 | 审计日志完整性、访问控制文档 |
| 等保三级 | 密码策略、会话超时、操作审计 |

## 9.9 总结

WeKnora 是一个**架构设计优秀、功能完备、代码质量较高**的企业级 RAG + Agent 框架。其核心优势在于：

1. **模块化**：所有外部依赖可插拔
2. **安全**：企业级 RBAC + 加密 + 审计
3. **可观测**：全链路追踪 + 运行时仪表盘
4. **灵活**：Lite/分布式双模式部署

主要改进空间在于：
1. **代码组织**：大文件拆分、错误处理统一
2. **性能优化**：嵌入缓存、流水线并行
3. **测试覆盖**：补充集成测试和性能基准
4. **运维体验**：配置简化、混沌工程
