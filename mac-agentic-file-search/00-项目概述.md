## 1. 项目背景与目标

### 1.1 问题陈述

在企业级知识管理与文档检索领域，传统的 RAG（Retrieval-Augmented Generation，检索增强生成）系统面临三大结构性瓶颈：

| 瓶颈 | 具体表现 | 业务影响 |
|------|----------|----------|
| **上下文碎片化** | 文档被机械切分为固定长度的 chunk，跨段落、跨章节的语义关联被切断 | 无法回答需要综合多章节信息的复杂问题 |
| **交叉引用盲区** | 法律文件、商业合同中常见的"参见 Exhibit B"、"详见附件三"等引用关系在嵌入向量空间中不可见 | 遗漏关键条款，导致法律/财务风险 |
| **语义相似 ≠ 逻辑相关** | 基于余弦相似度的检索可能返回字面相似但逻辑无关的内容 | 检索精度下降，产生幻觉答案 |

### 1.2 项目目标

FsExplorer 旨在构建一个 **Agent 驱动的动态文件探索系统**，其核心目标为：

1. **动态探索能力**：Agent 根据问题实时决定探索路径，而非依赖预计算的静态索引
2. **交叉引用追踪**：自动识别文档间的引用关系，按需回溯探索
3. **可验证输出**：每个事实声明均附带精确的源文件引用（文件名 + 章节/页码）
4. **双模式架构**：支持纯 Agentic 模式（无索引依赖）和索引加速模式（DuckDB 混合检索）
5. **成本透明**：完整的 Token 使用追踪与费用估算

### 1.3 项目定位

```
传统关键词搜索          传统RAG系统             FsExplorer
     │                     │                      │
     ▼                     ▼                      ▼
  字面匹配              语义嵌入                Agent 决策
  静态索引              预计算 chunk            动态探索
  无推理能力             单轮检索               多步推理
  无引用追踪             无交叉引用             自动回溯
```

## 2. 核心价值主张

### 2.1 Agentic 探索 vs 传统 RAG 对比

| 维度 | 传统 RAG 系统 | FsExplorer Agentic 模式 |
|------|--------------|------------------------|
| **索引策略** | 预计算嵌入向量，构建固定 chunk 索引 | 无预索引要求，实时解析文档 |
| **检索方式** | 单次向量相似度检索 | 多步推理 + 工具调用循环 |
| **上下文保持** | 固定窗口 chunk，跨 chunk 关联丢失 | 完整文档解析，保持章节结构 |
| **交叉引用** | 无法感知文档间引用关系 | 自动检测并回溯引用文档 |
| **决策逻辑** | 无（确定性检索） | LLM 驱动的动态决策 |
| **结果可解释性** | 黑盒（相似度分数） | 透明（推理路径 + 引用标注） |
| **冷启动成本** | 需要预先索引整个语料库 | 零冷启动，即问即答 |
| **更新延迟** | 索引重建延迟 | 实时反映文件系统变化 |
| **适用场景** | 大规模静态语料库、FAQ | 法律尽调、合同分析、深度研究 |

### 2.2 双模式融合优势

FsExplorer 创新性地提供 **Agentic + 索引** 双模式：

| 模式 | 数据流 | 适用场景 |
|------|--------|----------|
| **纯 Agentic** | 查询 → Agent → 工具调用 → 文件系统 → 答案 | 小规模文档集（<100文件）、一次性查询 |
| **索引加速** | 查询 → Agent → semantic_search → DuckDB → 答案 | 大规模语料库、频繁查询、需要元数据过滤 |
| **混合模式** | 索引初筛 + Agent 深度探索 | 兼顾效率与深度 |

### 3.2 用户旅程示例

```
法律尽调人员典型工作流：

1. 准备阶段
   └── 加载目标文件夹（含 30+ 合同/附件）

2. 索引构建（可选）
   └── explore index ./due_diligence/ --with-metadata
       ├── 自动解析所有 PDF/DOCX
       ├── 提取元数据（金额、日期、组织名等）
       └── 构建 DuckDB 索引 + Schema

3. 探索查询
   └── explore --task "收购价格是多少？包括所有调整项和托管金额"
       ├── Agent 调用 semantic_search 定位候选文档
       ├── parse_file 深度阅读主协议
       ├── 发现交叉引用 "见附件 B 价格调整公式"
       ├── 回溯探索附件 B
       └── 生成带引用的最终答案

4. 结果验证
   ├── 检查引用来源是否准确
   ├── 查看 Agent 推理路径
   └── 确认费用统计
```

### 5.2 架构模式详解

#### 5.2.1 事件驱动 Workflow 模式

系统核心使用 `llama-index-workflows` 实现的事件驱动架构：

- **Workflow**：定义探索流程的有限状态机
- **Steps**：装饰器标注的异步处理步骤
- **Events**：类型化的事件对象，驱动状态转换
- **Context**：工作流上下文，维护跨步骤状态
- **Resources**：可注入的共享资源（如 Agent 单例）

#### 5.2.2 工具调用 Agent 模式

Agent 遵循 ReAct（Reason + Act）模式：

1. **Reason**：LLM 生成推理过程（`reason` 字段）
2. **Act**：LLM 选择工具调用（`tool_name` + `tool_input`）
3. **Observe**：工具执行结果加入对话历史
4. **Loop**：重复 1-3 直到生成最终答案

#### 5.2.3 管道-过滤器索引模式

索引子系统采用管道-过滤器架构：

```
File Discovery → Parsing → Chunking → Metadata Extraction → Embedding → Storage
     │              │          │              │                │           │
  os.walk      Docling    SmartChunker   Heuristic +      GenAI        DuckDB
                            (1500/150)   langextract      Embedding    Upsert
```

#### 5.2.4 仓储与协议模式

存储层使用 Protocol（结构化子类型）定义接口契约：

- `StorageBackend` Protocol：定义存储操作接口
- `DuckDBStorage`：DuckDB 具体实现
- 未来可扩展：PostgreSQL、SQLite、远程存储等

## 6. 关键功能特性

### 6.1 九种工具能力

| 工具名称 | 类型 | 功能描述 | 参数 |
|----------|------|----------|------|
| `scan_folder` | 文档扫描 | 并行扫描文件夹内所有文档，返回预览摘要 | `directory`, `max_workers`, `preview_chars` |
| `preview_file` | 文档预览 | 快速预览单个文档（前 3000 字符） | `file_path`, `max_chars` |
| `parse_file` | 文档解析 | 解析完整文档内容为 Markdown | `file_path` |
| `read` | 文件读取 | 读取纯文本文件内容 | `file_path` |
| `grep` | 模式搜索 | 在文件中搜索正则表达式 | `file_path`, `pattern` |
| `glob` | 文件查找 | 按 glob 模式查找文件 | `directory`, `pattern` |
| `semantic_search` | 语义检索 | 在索引中执行语义搜索 + 元数据过滤 | `query`, `filters`, `limit` |
| `get_document` | 文档获取 | 通过 doc_id 获取完整索引文档 | `doc_id` |
| `list_indexed_documents` | 文档列表 | 列出当前语料库的所有索引文档 | 无 |

### 6.2 三阶段探索策略

| 阶段 | 策略 | 使用工具 | 输出 |
|------|------|----------|------|
| **Phase 1: 并行扫描** | 快速预览所有文档，分类相关性 | `scan_folder` | RELEVANT/MAYBE/SKIP 分类 |
| **Phase 2: 深度阅读** | 完整解析相关文档，提取关键信息 | `parse_file` | 关键信息 + 交叉引用发现 |
| **Phase 3: 回溯追踪** | 跟随交叉引用，探索被跳过的文档 | `preview_file` / `parse_file` | 完整信息链 |

### 6.3 混合检索能力

索引模式下的检索引擎支持三路并行：

1. **语义检索**：基于向量嵌入的余弦相似度
2. **关键词检索**：基于 SQL LIKE 的词项匹配
3. **元数据过滤**：基于 JSON 路径的精确过滤

检索结果通过加权评分公式合并：
```
combined_score = semantic_score × 100 + metadata_score × 10
```

### 6.4 元数据提取能力

| 提取方式 | 字段类型 | 内容 |
|----------|----------|------|
| **启发式提取** | 基础字段 | filename, extension, document_type, file_size_bytes, mentions_currency, mentions_dates |
| **langextract 提取** | 实体字段 | lx_organizations, lx_people, lx_deal_terms, lx_money_mentions, lx_date_mentions |
| **langextract 提取** | 布尔字段 | lx_has_earnout, lx_has_escrow, lx_enabled |
| **自动 Schema** | 动态发现 | 根据语料库内容自动生成提取配置 |

### 6.5 实时通信能力

WebSocket 端点 `/ws/explore` 提供：

- **流式事件输出**：ToolCallEvent、GoDeeperEvent、AskHumanEvent 实时推送
- **交互式人机对话**：支持 Agent 提问 → 用户回答 → Agent 继续
- **执行统计**：实时 Token 消耗、API 调用次数
- **探索轨迹**：完整的工具调用路径记录

### 6.6 引用与可追溯性

强制引用格式确保结果可验证：

```
[Source: filename.pdf, Section 2.1]
```

最终答案包含：
1. 直接回答
2. 带引用的详细论据
3. 来源清单（Sources Consulted）

## 7. 非功能性需求

### 7.1 性能需求

| 指标 | 目标值 | 实现方式 |
|------|--------|----------|
| 单文档解析 | < 5 秒 | Docling 本地解析 + 缓存 |
| 并行扫描吞吐量 | 4 文档/批次 | ThreadPoolExecutor (4 workers) |
| 索引构建速度 | > 50 文档/分钟 | 并行元数据提取 + 批量嵌入 |
| 查询响应时间 | < 30 秒（简单） | 工具调用循环 + 缓存 |
| 工作流超时 | 300 秒 | 可配置超时机制 |
| 内存占用 | < 512MB | 流式处理 + 缓存控制 |

### 7.2 扩展性需求

| 维度 | 设计 | 说明 |
|------|------|------|
| **工具扩展** | 注册表模式 | 新增工具仅需：实现函数 → 注册到 TOOLS → 更新类型别名 → 更新 SYSTEM_PROMPT |
| **存储扩展** | Protocol 接口 | 实现 `StorageBackend` 即可替换存储后端 |
| **LLM 扩展** | 抽象客户端 | 当前绑定 Gemini，可适配 OpenAI/Anthropic |
| **文档格式** | Docling 驱动 | 新增格式只需添加到 `SUPPORTED_EXTENSIONS` |
| **并发扩展** | 异步架构 | asyncio + ThreadPoolExecutor 支持高并发 |

### 7.3 安全性需求

| 安全域 | 措施 |
|--------|------|
| **API 密钥管理** | 环境变量 + `.env` 文件，不硬编码 |
| **数据隐私** | 文档本地解析（Docling），不上传第三方 |
| **文件系统隔离** | 仅访问用户指定的目录，无越权操作 |
| **输入验证** | Pydantic 模型验证所有 LLM 输出 |
| **错误隔离** | 工具调用异常捕获，不中断工作流 |

### 7.4 可维护性需求

| 实践 | 工具 | 说明 |
|------|------|------|
| **代码风格** | ruff | 统一格式化与 lint |
| **类型检查** | ty | 静态类型安全 |
| **测试覆盖** | pytest | 单元测试 + 集成测试 + E2E 测试 |
| **提交检查** | pre-commit | 自动化质量门禁 |
| **文档** | Markdown | 架构文档 + 代码注释 + Docstring |

### 7.5 可用性需求

| 方面 | 设计 |
|------|------|
| **CLI 体验** | Rich 渲染的彩色面板、进度条、图标 |
| **Web UI** | 单文件 HTML，无需构建步骤 |
| **错误提示** | 中文化错误信息，工具错误不中断流程 |
| **配置简化** | 合理的默认值，最小化必需配置 |
| **可观测性** | Token 追踪、探索轨迹、引用提取 |
