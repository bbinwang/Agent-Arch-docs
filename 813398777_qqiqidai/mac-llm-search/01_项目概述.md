## 1.1 项目目标与核心价值

### 1.1.1 项目定位

**pyLLMSearch**（包名 `pyllmsearch`）是一个 **LLM 驱动的先进 RAG（Retrieval-Augmented Generation，检索增强生成）应用**。其核心定位是：让用户通过简单的 **YAML 配置文件**，即可在本地文档集合上构建问答系统，无需编写代码。

### 1.1.2 解决的问题

传统 RAG 系统存在以下痛点，pyLLMSearch 逐一应对：

| 痛点 | pyLLMSearch 的解决方案 |
|------|------------------------|
| 基础 RAG 检索质量差 | 引入 **Hybrid Search（稀疏+密集）**、**HyDE**、**MultiQuery**、**Re-ranking** |
| 文档解析不精细 | 内置 Markdown/PDF/DOCX 专用解析器，支持逻辑分片、表格提取、图片解析 |
| 索引更新需全量重建 | 基于 **文件 Hash** 的增量更新，只处理变更文件 |
| 无法跳转到原文 | **Deep Linking** 支持跳转到 PDF 页码或 Markdown 标题 |
| 模型选择受限 | 支持 OpenAI、Azure OpenAI、HuggingFace、LlamaCPP、LiteLLM/Ollama 等 |
| 交互方式单一 | 提供 CLI、Web UI（Streamlit）、FastAPI、MCP Server 四种交互方式 |

### 1.1.3 核心价值主张

1. **配置驱动**：通过 YAML 文件即可配置整个 RAG 流水线，无需编码
2. **本地优先**：支持本地 LLM 模型，数据不出本地，保护隐私
3. **生产级检索**：超越基础语义搜索，集成多种先进检索增强技术
4. **多模态支持**：文本、表格、图片均可解析和检索
5. **开放集成**：通过 MCP 协议与 Cursor、Windsurf、VSCode Copilot 等工具集成

## 1.4 架构风格及理由

### 1.4.1 整体架构风格

pyLLMSearch 采用 **管道-过滤器（Pipe-Filter）+ 插件式（Plugin）+ 配置驱动（Configuration-Driven）** 的混合架构风格。

```
┌─────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌─────────┐
│  配置层  │ → │  解析层   │ → │  嵌入层   │ → │  检索层   │ → │  生成层  │
│  YAML   │    │ Parsers  │    │Embed/SPLADE│   │Ranking   │    │  LLM    │
└─────────┘    └──────────┘    └──────────┘    └──────────┘    └─────────┘
```

### 1.4.2 架构风格理由

| 风格 | 理由 |
|------|------|
| **管道-过滤器** | RAG 流水线天然是线性流程（解析→嵌入→检索→生成），每层独立处理 |
| **插件式** | 文档解析器（Markdown/PDF/DOCX/Unstructured）可插拔，通过扩展名自动路由 |
| **配置驱动** | 用户无需编码即可通过 YAML 配置整个流水线，降低使用门槛 |
| **策略模式** | 嵌入模型、重排序模型、LLM 模型均可通过配置切换 |
| **依赖注入** | LLMBundle 封装所有运行时依赖，通过 FastAPI Depends 注入 |

### 1.4.3 设计原则

1. **单一职责**：每个模块只负责一个功能（解析、嵌入、检索、生成）
2. **开闭原则**：新增解析器/模型无需修改现有代码，只需实现接口
3. **依赖倒置**：高层模块依赖抽象（AbstractLLMModel、VectorStore），不依赖具体实现
4. **接口隔离**：解析器、模型、存储都有最小化接口

## 1.5 关键功能特性

### 1.5.1 核心功能列表

| # | 功能 | 描述 | 对应模块 |
|---|------|------|----------|
| 1 | **文档解析** | 支持 MD/PDF/DOCX 等格式，逻辑分片保留结构 | `parsers/` |
| 2 | **密集嵌入** | 支持 HF/SentenceTransformer/Instructor/OpenAI 嵌入 | `embeddings.py` |
| 3 | **稀疏嵌入** | SPLADE 稀疏向量检索 | `splade.py` |
| 4 | **混合检索** | 稀疏+密集并行检索，结果取并集 | `ranking.py` |
| 5 | **重排序** | Cross-encoder 重排序（MARCO/BGE/Zerank-2） | `ranking.py` |
| 6 | **HyDE** | 假设文档嵌入，提升检索质量 | `process.py` |
| 7 | **MultiQuery** | 多查询变体，RAG Fusion 风格 | `process.py` |
| 8 | **增量更新** | 基于文件 Hash 的索引增量更新 | `embeddings.py` |
| 9 | **对话历史** | 多轮对话上下文、查询重写 | `process.py` |
| 10 | **Deep Linking** | 跳转到 PDF 页码或 Markdown 标题 | `config.py` |
| 11 | **表格解析** | GMFT/Azure Document Intelligence 表格提取 | `parsers/tables/` |
| 12 | **图片解析** | Gemini API 图片内容提取 | `parsers/images/` |
| 13 | **MCP 集成** | 通过 MCP 协议与 IDE 客户端交互 | `api.py` |
| 14 | **响应持久化** | SQLite 存储问答记录供分析 | `database/` |

### 1.5.2 支持的文档格式

| 格式 | 解析器类型 | 特点 |
|------|------------|------|
| `.md` | 内置逻辑解析器 | 按标题层级递归分片，保留代码块 |
| `.pdf` | MuPDF 解析器 | 支持表格/图片区域过滤 |
| `.docx` | 内置递归解析器 | 支持嵌套表格、标题层级 |
| `.doc` | 同 DOCX | 兼容处理 |
| 其他 | Unstructured | 自动分区（CSV/HTML/Email 等） |

### 1.5.3 支持的 LLM 模型

| 类型 | 配置标识 | 后端 |
|------|----------|------|
| OpenAI | `openai` | ChatOpenAI |
| Azure OpenAI | `azureopenai` | AzureChatOpenAI |
| HuggingFace | `huggingface` | HuggingFacePipeline |
| LlamaCPP | `llamacpp` | llama-cpp-python |
| LiteLLM/Ollama | 通过 OpenAI 兼容 API | ChatOpenAI |

## 1.6 非功能性需求

### 1.6.1 性能

| 指标 | 目标 | 实现方式 |
|------|------|----------|
| **索引速度** | 数 GB 文档快速处理 | 批量嵌入、多线程图片解析 |
| **检索延迟** | 秒级响应 | ChromaDB 本地检索、SPLADE 稀疏索引 |
| **嵌入吞吐** | GPU 加速 | 批量推理、CUDA 支持 |
| **内存管理** | 避免 OOM | 显式卸载模型、gc.collect、torch.cuda.empty_cache |

### 1.6.2 扩展性

| 维度 | 扩展方式 |
|------|----------|
| **新文档格式** | 实现解析器函数，注册到 `_splitter_conf` |
| **新嵌入模型** | 在 `MODELS` 字典注册新类型 |
| **新 LLM** | 继承 `AbstractLLMModel`，注册到 `model_mappings` |
| **新重排序器** | 实现 `get_scores` 接口，注册到 `get_llm_bundle` |
| **新表格解析器** | 在 `PARSER_MAPPING` 注册新解析器 |

### 1.6.3 安全性

| 方面 | 措施 |
|------|------|
| **API 密钥** | 通过 `.env` 环境变量管理，不硬编码 |

| **输入校验** | Pydantic 模型验证所有配置输入 |
| **CORS** | API 默认允许所有来源（可配置） |

### 1.6.4 可用性

## 1.9 本章小结

pyLLMSearch 是一个功能完备、架构清晰的先进 RAG 系统。其核心价值在于：

1. **零代码配置**：YAML 驱动，降低使用门槛
2. **检索质量优先**：混合检索 + 重排序 + HyDE/MultiQuery
