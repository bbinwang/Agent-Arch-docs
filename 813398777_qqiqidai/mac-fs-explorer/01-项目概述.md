## 1. 项目背景与目标

### 1.1 项目定位

**fs-explorer** 是一个基于大语言模型（LLM）的命令行智能体（CLI Agent），其核心使命是帮助用户高效地探索和理解本地文件系统的内容。与传统的 `find`、`grep`、`cat` 等命令行工具不同，fs-explorer 引入了 AI 驱动的自主决策能力，能够：

1. **理解自然语言任务**: 用户可以用自然语言描述需求（如"找到包含投诉的 PDF 文件并总结"），无需记忆复杂的命令语法。
2. **自主规划探索路径**: Agent 根据任务目标，自主决定是读取文件、搜索内容、深入子目录，还是请求用户澄清。
3. **处理多格式文档**: 不仅支持纯文本文件，还能通过 LlamaParse 服务解析 PDF、DOCX、PPTX、XLSX 等复杂格式。
4. **透明化决策过程**: 通过 Rich 库在终端实时渲染 Agent 的每一步操作和推理过程。

### 1.2 核心价值主张

| 维度 | 传统方式 | fs-explorer 方式 |
|------|---------|-----------------|
| **交互模式** | 用户需精确指定命令和参数 | 用户描述意图，Agent 自主执行 |
| **文件发现** | 依赖 `find` + `glob` 模式匹配 | 基于语义理解的文件定位 |
| **内容理解** | 用户自行阅读和判断 | Agent 自动提取关键信息并总结 |
| **格式支持** | 仅文本文件 | 文本 + PDF/PPTX/DOCX/XLSX |
| **决策透明度** | 无（命令直接执行） | 高（每步操作附带推理原因） |

### 1.3 解决的问题

1. **信息过载**: 当目录包含大量文件时，人工逐一检查效率极低。fs-explorer 通过 Agent 的自主决策，快速缩小搜索范围。
2. **格式壁垒**: 传统命令行工具无法直接处理二进制文档格式。fs-explorer 通过 LlamaParse 将非结构化文档转为可搜索文本。
3. **语义鸿沟**: 用户知道要找什么，但不确定文件在哪里或文件名是什么。fs-explorer 通过内容搜索（grep）和语义理解弥合这一差距。
4. **探索不确定性**: 面对陌生目录结构，用户不知道从哪里开始。fs-explorer 的 Agent 会先描述目录内容，再决定下一步。

### 1.4 目标用户

| 用户类型 | 使用场景 | 核心需求 |
|---------|---------|---------|
| **数据分析师** | 在大量报告中查找特定数据点 | 快速定位、精准提取 |
| **法务/合规人员** | 在合同和文书中查找特定条款 | 格式支持、内容准确性 |
| **研究人员** | 在论文集合中查找相关研究 | 语义搜索、批量处理 |
| **系统管理员** | 在日志和配置文件中排查问题 | 模式匹配、递归搜索 |
| **AI 开发者** | 评估 Agentic Search vs RAG 的性能 | 评估框架、对比分析 |

## 3. 项目架构风格及理由

### 3.1 架构风格总览

fs-explorer 采用 **事件驱动的工作流编排（Event-Driven Workflow Orchestration）** 风格，并融合了 **Agent 智能体模式** 和 **管道-过滤器模式（Pipes and Filters）**。

```
┌─────────────────────────────────────────────────────────┐
│                    架构风格分层                           │
├─────────────────────────────────────────────────────────┤
│  Layer 3: Agent Pattern (智能体模式)                     │
│  ┌───────────────────────────────────────────────────┐  │
│  │  LLM 决策循环: 感知 → 推理 → 行动 → 观察 → 循环    │  │
│  └───────────────────────────────────────────────────┘  │
│  Layer 2: Event-Driven Workflow (事件驱动工作流)         │
│  ┌───────────────────────────────────────────────────┐  │
│  │  步骤(Step) ← 事件(Event) → 步骤(Step) → ...      │  │
│  └───────────────────────────────────────────────────┘  │
│  Layer 1: CLI + Rich Rendering (命令行交互层)            │
│  ┌───────────────────────────────────────────────────┐  │
│  │  用户输入 → Typer 解析 → 异步执行 → Rich 渲染      │  │
│  └───────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
```

### 3.2 事件驱动工作流

**设计理由**:

1. **状态隔离**: 每个步骤（`@step` 装饰的函数）是无状态的，状态通过 `Context[WorkflowState]` 集中管理，避免全局变量污染。
2. **事件溯源**: 所有中间事件（`ToolCallEvent`、`GoDeeperEvent`、`AskHumanEvent`）都被写入事件流，可被外部观察者消费，实现执行过程的可观测性。
3. **人机协作**: `InputRequiredEvent` / `HumanResponseEvent` 机制天然支持 Human-in-the-Loop 场景，Agent 可以在不确定时暂停并请求用户输入。
4. **可扩展性**: 新增步骤只需添加 `@step` 装饰的函数并定义输入/输出事件类型，无需修改现有代码。

**核心抽象**:

- `Workflow`: 工作流基类，管理步骤注册、事件路由、超时控制。
- `Context[T]`: 类型化的工作流上下文，提供状态存储和事件写入能力。
- `Event`: 事件基类，所有自定义事件继承自此类。
- `StartEvent` / `StopEvent`: 工作流生命周期标记事件。
- `Resource`: 依赖注入机制，将共享资源（如 Agent 实例）注入到步骤中。

### 3.3 Agent 智能体模式

**设计理由**:

1. **自主决策**: Agent 根据当前对话历史和目录描述，自主决定下一步动作，无需预定义规则。
2. **工具使用**: Agent 被赋予一组文件系统工具（read/glob/grep/parse_file），可以按需调用。
3. **反思能力**: 每次工具调用后结果被追加到对话历史，Agent 可以基于工具输出调整策略。
4. **安全边界**: Agent 的能力被严格限制在工具集范围内，无法执行任意代码。

**决策循环**:

```
用户任务 → 目录描述 → LLM 决策 → 动作执行 → 结果观察 → LLM 决策 → ... → 最终结果
```

### 3.4 管道-过滤器模式（RAG 部分）

**设计理由**:

1. **阶段分离**: 索引阶段（Parse → Chunk → Embed → Upload）和检索阶段（Filter → Search → Rerank → Generate）清晰分离。
2. **可替换性**: 每个阶段（如 Embedder、VectorDB）都是可替换的接口实现，便于切换模型或数据库。
3. **可测试性**: 每个过滤器可以独立测试，输入输出类型明确。

### 3.5 Monorepo 结构

**设计理由**:

1. **代码复用**: `fs-explorer` 和 `rag-starterkit` 共享缓存机制，`eval-framework` 依赖前两者。
2. **独立发布**: 每个包有独立的 `pyproject.toml`，可单独版本化和发布。
3. **统一工具链**: 根目录的 `Makefile` 和 `pre-commit-config.yaml` 统一管理所有包的开发流程。
4. **工作区管理**: 通过 `uv workspace` 实现跨包依赖解析和统一虚拟环境。

## 4. 关键功能特性

### 4.1 核心功能矩阵

| 功能 | 命令/模块 | 描述 | 优先级 |
|------|----------|------|--------|
| **智能探索** | `explore run` | AI Agent 自主探索文件系统完成任务 | P0 |
| **文件读取** | `read` 工具 | 读取文本文件内容 | P0 |
| **内容搜索** | `grep` 工具 | 正则表达式搜索文件内容 | P0 |
| **模式匹配** | `glob` 工具 | 文件名模式匹配 | P0 |
| **文档解析** | `parse_file` 工具 | 解析 PDF/PPTX/DOCX/XLSX | P0 |
| **缓存加载** | `explore load-cache` | 预解析文件到持久缓存 | P1 |
| **缓存查询** | `explore get-cached` | 查看已缓存文件内容 | P2 |
| **RAG 索引** | `rag-starterkit` | 构建向量索引 | P1 |
| **RAG 查询** | `rag-starterkit` | 混合检索 + LLM 回答 | P1 |
| **评估执行** | `run-eval` | 双框架对比评估 | P1 |
| **统计报告** | `get-stats` | 生成评估报告 | P2 |
| **arXiv 缓存** | `cache-arxiv` | 批量缓存论文摘要 | P2 |

### 4.2 Agent 动作类型

| 动作 | 类型标识 | 触发条件 | 结果 |
|------|---------|---------|------|
| **Tool Call** | `toolcall` | Agent 需要与文件系统交互 | 调用指定工具，结果追加到对话历史 |
| **Go Deeper** | `godeeper` | Agent 需要进入子目录 | 更新当前目录状态，重新描述目录内容 |
| **Ask Human** | `askhuman` | Agent 不确定或需要澄清 | 暂停执行，等待用户输入 |
| **Stop** | `stop` | Agent 认为任务完成 | 返回最终结果，结束工作流 |

### 4.3 工具集详细说明

| 工具名 | 参数 | 返回值 | 用途 |
|--------|------|--------|------|
| `read` | `file_path: str` | 文件内容字符串 | 读取文本文件 |
| `grep` | `file_path: str`, `pattern: str` | 匹配行列表 | 正则搜索文件内容 |
| `glob` | `directory: str`, `pattern: str` | 匹配文件路径列表 | 文件名模式匹配 |
| `check_api_key` | 无 | API Key 状态信息 | 检查 LlamaParse API Key 是否配置 |
| `parse_file` | `file_path: str` | 解析后的文本内容 | 解析非结构化文档（优先从缓存读取） |

## 5. 非功能性需求

### 5.1 性能

| 指标 | 目标值 | 当前状态 | 说明 |
|------|--------|---------|------|
| **Agent 首次响应** | < 5s | 取决于 Gemini API | 首次 LLM 调用延迟 |
| **工具调用延迟** | < 1s（本地工具） | ✅ 满足 | 本地文件 I/O 极快 |
| **parse_file（缓存命中）** | < 100ms | ✅ 满足 | DiskCache 读取 |
| **parse_file（缓存未命中）** | < 30s | 取决于 LlamaParse | 网络 API 调用 |
| **RAG 索引吞吐量** | > 10 docs/min | 受 API 限流 | 并发度为 5 |
| **RAG 查询延迟** | < 3s | ✅ 满足 | 向量检索 + LLM 生成 |

## 7. 技术亮点总结

1. **事件驱动 Agent 架构**: 将 Agent 决策循环建模为事件驱动的工作流，每个决策步骤是一个独立的事件处理器，实现了决策逻辑与执行逻辑的解耦。

2. **混合检索 RAG**: 结合 Dense（OpenAI Embedding）和 Sparse（BM25）两种检索方式，通过 RRF 融合提升检索精度。

3. **LLM-as-Judge 评估**: 使用 GPT-5.2 作为自动化评估者，对 Agent 和 RAG 的回答进行正确性和相关性评分。

4. **渐进式缓存**: 支持预解析文件到磁盘缓存，避免重复的 API 调用，提升响应速度并降低成本。

5. **人机协作**: Agent 在遇到不确定情况时可以暂停并请求用户澄清，实现 Human-in-the-Loop。

6. **Monorepo + uv workspace**: 使用现代 Python 工具链管理多包项目，统一依赖解析和开发体验。

7. **类型安全**: 全面使用 Type Hints、Pydantic 模型和静态类型检查，在开发期捕获类型错误。
