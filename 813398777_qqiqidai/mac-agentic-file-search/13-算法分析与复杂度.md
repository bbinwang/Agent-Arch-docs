## 2. SmartChunker.chunk_text() — 段落感知分块算法

### 2.1 算法描述

`SmartChunker.chunk_text()` 是索引管道中的核心分块算法，负责将解析后的长文本切分为适合嵌入和检索的文本块（chunk）。该算法的核心特性是 **段落感知（paragraph-aware）**：它不会在段落中间粗暴切割，而是优先在双换行符（`\n\n`，即段落边界）处进行分割，从而保持语义完整性。

算法采用滑动窗口策略，维护一个起始指针 `start`，每次尝试取 `chunk_size` 长度的文本。如果尚未到达文本末尾，则在 `[start + chunk_size//2, start + chunk_size]` 区间内反向搜索最近的段落边界（`\n\n`）。若找到，则在边界处切割；否则在 `tentative_end` 处硬切割。切割后，下一个块的起始位置回退 `overlap` 字符，以保证块间重叠，避免跨块信息丢失。

### 2.2 伪代码

```
function chunk_text(text, chunk_size=1500, overlap=150):
    normalized = text.strip()
    chunks = []
    start = 0
    position = 0

    while start < len(normalized):
        tentative_end = min(start + chunk_size, len(normalized))
        end = tentative_end

        if tentative_end < len(normalized):
            # 在后半段搜索最近的段落边界
            boundary = normalized.rfind("\n\n", start + chunk_size//2, tentative_end)
            if boundary != -1:
                end = boundary + 2  # 包含换行符

        chunk = normalized[start:end].strip()
        if chunk:
            chunks.append(TextChunk(
                text=chunk,
                position=position,
                char_start=start,
                char_end=end
            ))
            position += 1

        if end >= len(normalized):
            break

        # 下一个起始位置回退 overlap 字符
        start = max(0, end - overlap)

    return chunks
```

### 2.3 时间复杂度分析

设文本长度为 $n$，分块大小为 $c$（chunk_size），重叠大小为 $o$（overlap）。

| 操作 | 单次代价 | 执行次数 | 总代价 |
|------|----------|----------|--------|
| `text.strip()` | $O(n)$ | 1 | $O(n)$ |
| `rfind("\n\n", ...)` | $O(c)$ | $\lceil n/(c-o) \rceil$ | $O(n \cdot c / (c-o))$ |
| 切片 `normalized[start:end]` | $O(c)$ | $\lceil n/(c-o) \rceil$ | $O(n \cdot c / (c-o))$ |
| `chunk.strip()` | $O(c)$ | $\lceil n/(c-o) \rceil$ | $O(n \cdot c / (c-o))$ |

由于 $c$ 和 $o$ 是常数（默认 1500 和 150），$c/(c-o) \approx 1.1$ 为常数因子。

**总时间复杂度：$O(n)$**

严格来说是 $O(n \cdot \frac{c}{c-o})$，但由于 $c$ 和 $o$ 是固定参数，渐进复杂度为线性。

### 2.4 空间复杂度分析

| 数据 | 空间 |
|------|------|
| 输入文本（normalized） | $O(n)$ |
| 所有 chunk 对象 | $O(n)$（所有 chunk 文本总和 ≈ $n + (n/(c-o)) \cdot o \approx n \cdot c/(c-o)$） |
| 辅助变量 | $O(1)$ |

**总空间复杂度：$O(n)$**

### 2.5 优化建议

| 优先级 | 优化方向 | 预期收益 | 实现复杂度 |
|--------|----------|----------|------------|
| **高** | 基于 Token 的分块（使用 tiktoken 等 tokenizer） | 与 LLM 上下文窗口对齐，避免截断 Token | 中 |
| **中** | 多模式边界检测（支持 `\n\n`、`\n`、`.`、`。`） | 对无段落结构的文本更友好 | 低 |
| **中** | 使用 KMP/Boyer-Moore 加速边界搜索 | 对大 chunk_size 有边际收益 | 低 |
| **低** | 流式生成器（yield 替代 append） | 降低峰值内存（不存储全部分块） | 低 |
| **低** | 自适应 chunk_size（根据文档类型调整） | 技术文档 vs 法律合同使用不同粒度 | 中 |

## 3. 并行文档扫描 (scan_folder)

### 3.1 算法描述

`scan_folder()` 是文件系统扫描的核心函数，负责并行扫描指定文件夹内所有支持的文档文件，并返回每个文件的预览摘要。该算法采用 **ThreadPoolExecutor + as_completed** 模式实现并行处理：

1. **文件发现**：使用 `os.walk()` 或 `Path.rglob()` 遍历目录树，筛选出支持的文件扩展名（PDF/DOCX/PPTX/XLSX/HTML/MD）。
2. **任务提交**：将每个文件的解析任务提交到线程池，线程池大小由 `max_workers` 参数控制（默认 4）。
3. **结果收集**：使用 `as_completed()` 迭代器按完成顺序收集结果，而非提交顺序，最大化响应速度。
4. **缓存检查**：每个文件解析前检查 `_DOCUMENT_CACHE`，若文件未修改则直接返回缓存结果。

### 3.2 伪代码

```
function scan_folder(directory, max_workers=4, preview_chars=300):
    # 1. 文件发现
    supported_exts = {'.pdf', '.docx', '.pptx', '.xlsx', '.html', '.md'}
    files = []
    for path in Path(directory).rglob("*"):
        if path.suffix.lower() in supported_exts:
            files.append(path)

    results = {}
    futures = {}

    # 2. 并行提交
    with ThreadPoolExecutor(max_workers=max_workers) as executor:
        for file_path in files:
            future = executor.submit(parse_and_preview, file_path, preview_chars)
            futures[future] = file_path

        # 3. 按完成顺序收集
        for future in as_completed(futures):
            file_path = futures[future]
            try:
                result = future.result(timeout=30)
                results[str(file_path)] = result
            except Exception as e:
                results[str(file_path)] = {"error": str(e)}

    return results

function parse_and_preview(file_path, preview_chars):
    # 4. 缓存检查
    cache_key = f"{file_path}:{file_path.stat().st_mtime}"
    if cache_key in _DOCUMENT_CACHE:
        return _DOCUMENT_CACHE[cache_key]

    # 5. 解析文档
    document = docling_parse(file_path)
    preview = document.text[:preview_chars]

    result = {
        "preview": preview,
        "size": len(document.text),
        "type": file_path.suffix
    }
    _DOCUMENT_CACHE[cache_key] = result
    return result
```

### 3.3 时间复杂度分析

设文件数为 $n$，线程数为 $k$（max_workers），单文件解析时间为 $p$（高度依赖文件大小和格式）。

| 阶段 | 复杂度 | 说明 |
|------|--------|------|
| 文件发现（os.walk） | $O(n)$ | 线性遍历 |
| 任务提交 | $O(n)$ | 每个文件提交一次 |
| 并行解析 | $O(\lceil n/k \rceil \cdot p)$ | 理想并行 |
| 结果收集 | $O(n)$ | as_completed 迭代 |

**总时间复杂度：$O(n + \lceil n/k \rceil \cdot p)$**

当 $n \gg k$ 时，主导项为 $O(n \cdot p / k)$。理想情况下（完全并行），加速比接近 $k$。

### 3.4 空间复杂度分析

| 数据 | 空间 |
|------|------|
| 文件列表 | $O(n)$ |
| Future 对象 | $O(n)$ |
| 结果字典 | $O(n \cdot preview\_chars)$ |
| 线程池 | $O(k)$ |

**总空间复杂度：$O(n \cdot preview\_chars)$**

### 3.5 优化建议

| 优先级 | 优化方向 | 预期收益 | 实现复杂度 |
|--------|----------|----------|------------|
| **高** | 使用 ProcessPoolExecutor 替代 ThreadPoolExecutor | Docling 解析是 CPU 密集型，绕过 GIL 可获得真正并行 | 中 |
| **高** | 异步 I/O（asyncio + aiofiles） | 减少线程开销，支持更高并发 | 中 |
| **中** | 文件大小预过滤（跳过超大文件） | 避免单个大文件阻塞整个批次 | 低 |
| **中** | 优先级队列（小文件优先） | 提高早期响应速度 | 低 |
| **低** | 增量扫描（仅处理修改的文件） | 重复扫描场景大幅加速 | 中 |

## 4. 元数据过滤DSL解析器 (parse_metadata_filters)

### 4.1 算法描述

`parse_metadata_filters()` 负责将人类可读的过滤表达式字符串解析为结构化的 `MetadataFilter` 对象列表。该解析器支持丰富的操作符：

| 操作符 | 含义 | 示例 |
|--------|------|------|
| `=` | 相等 | `document_type=contract` |
| `!=` | 不相等 | `extension!=.pdf` |
| `>` `>=` `<` `<=` | 比较 | `file_size_bytes>=10000` |
| `in` | 成员 | `extension in (.pdf, .docx)` |
| `~` | 子串匹配 | `filename~agreement` |

解析过程分为两个阶段：
1. **条件分割**（`_split_conditions`）：按逗号分割顶层条件，但忽略括号、引号内的逗号。
2. **单条件解析**：对每个条件提取字段名、操作符、值。

### 4.2 伪代码

```
function parse_metadata_filters(filter_string, allowed_fields):
    if not filter_string or not filter_string.strip():
        return []

    conditions = _split_conditions(filter_string.strip())
    filters = []

    for condition in conditions:
        condition = condition.strip()
        if not condition:
            continue

        # 匹配操作符（按长度降序，避免 >= 被 > 截断）
        for op in [">=", "<=", "!=", "=", ">", "<", "~"]:
            if op in condition:
                parts = condition.split(op, 1)
                if len(parts) == 2:
                    field = parts[0].strip()
                    value = parts[1].strip().strip("'\"")
                    break
        else:
            # 处理 "field in (a, b, c)" 格式
            match = re.match(r"(\w+)\s+in\s+\((.+)\)", condition)
            if match:
                field = match.group(1)
                value = [v.strip().strip("'\"") for v in match.group(2).split(",")]
                op = "in"
            else:
                raise ParseError(f"无法解析条件: {condition}")

        if field not in allowed_fields:
            raise ValidationError(f"未知字段: {field}")

        filters.append(MetadataFilter(field=field, op=op, value=value))

    return filters

function _split_conditions(text):
    """按逗号分割，但忽略括号/引号内的逗号"""
    conditions = []
    current = []
    depth_paren = 0    # 小括号深度
    depth_bracket = 0  # 中括号深度
    in_quote = None    # 当前引号字符（' 或 "）

    for char in text:
        if in_quote:
            current.append(char)
            if char == in_quote:
                in_quote = None
        elif char in "'\"":
            in_quote = char
            current.append(char)
        elif char == '(':
            depth_paren += 1
            current.append(char)
        elif char == ')':
            depth_paren -= 1
            current.append(char)
        elif char == '[':
            depth_bracket += 1
            current.append(char)
        elif char == ']':
            depth_bracket -= 1
            current.append(char)
        elif char == ',' and depth_paren == 0 and depth_bracket == 0:
            conditions.append(''.join(current))
            current = []
        else:
            current.append(char)

    if current:
        conditions.append(''.join(current))

    return conditions
```

### 4.3 时间复杂度分析

设过滤字符串长度为 $n$，条件数为 $m$。

| 操作 | 复杂度 | 说明 |
|------|--------|------|
| `_split_conditions` | $O(n)$ | 单遍扫描，每个字符常数时间处理 |
| 单条件解析 | $O(L)$ | L 为条件长度，操作符匹配为常数（固定 7 个操作符） |
| 所有条件解析 | $O(n)$ | 所有条件长度之和 = n |
| 成员检查（in allowed_fields） | $O(1)$ | allowed_fields 为 set |

**总时间复杂度：$O(n)$**

### 4.4 空间复杂度分析

| 数据 | 空间 |
|------|------|
| 条件列表 | $O(m)$ |
| 当前条件缓冲区 | $O(L_max) ⊆ O(n)$ |
| 结果过滤器列表 | $O(m)$ |

**总空间复杂度：$O(n)$**（最坏情况：整个字符串是一个条件）

### 4.5 优化建议

| 优先级 | 优化方向 | 预期收益 | 实现复杂度 |
|--------|----------|----------|------------|
| **高** | 使用正式解析库（pyparsing / lark / PLY） | 更健壮的语法支持，更好的错误信息 | 中 |
| **中** | 预编译正则表达式 | 重复解析场景减少开销 | 低 |
| **中** | 支持更复杂的逻辑（AND/OR/NOT 组合） | 满足高级过滤需求 | 高 |
| **低** | 缓存解析结果（相同字符串直接返回） | 重复查询场景加速 | 低 |

## 5. 检索合并排序 (_merge_and_rank)

### 5.1 算法描述

`_merge_and_rank()` 是混合检索引擎的核心合并算法，负责将来自不同检索路径的结果合并为统一排序的候选列表。系统支持三路检索：

1. **语义检索结果**：基于向量相似度，每个结果带有 `semantic_score`（0~1）。
2. **关键词检索结果**：基于词项匹配，每个结果带有 `keyword_score`。
3. **元数据过滤结果**：基于精确匹配，每个结果带有 `metadata_score`（0 或 1）。

合并策略使用 **哈希表去重 + 加权评分**：
- 以 `doc_id` 为键，将多路径结果聚合到同一 `RankedDocument` 对象。
- 使用加权公式计算综合得分：`combined_score = semantic_score × 100 + metadata_score × 10`。
- 按综合得分降序排序，返回 Top-K 结果。

### 5.2 伪代码

```
function _merge_and_rank(semantic_results, keyword_results, metadata_results, limit=10):
    # 1. 哈希表聚合
    doc_map = {}  # doc_id → RankedDocument

    for result in semantic_results:
        doc_id = result.doc_id
        if doc_id not in doc_map:
            doc_map[doc_id] = RankedDocument(doc_id=doc_id, semantic_score=0, metadata_score=0)
        doc_map[doc_id].semantic_score = max(doc_map[doc_id].semantic_score, result.score)

    for result in keyword_results:
        doc_id = result.doc_id
        if doc_id not in doc_map:
            doc_map[doc_id] = RankedDocument(doc_id=doc_id, semantic_score=0, metadata_score=0)
        doc_map[doc_id].keyword_score = max(doc_map[doc_id].keyword_score, result.score)

    for result in metadata_results:
        doc_id = result.doc_id
        if doc_id not in doc_map:
            doc_map[doc_id] = RankedDocument(doc_id=doc_id, semantic_score=0, metadata_score=0)
        doc_map[doc_id].metadata_score = max(doc_map[doc_id].metadata_score, result.score)

    # 2. 计算综合得分
    for doc in doc_map.values():
        doc.combined_score = doc.semantic_score * 100 + doc.metadata_score * 10

    # 3. 排序并返回 Top-K
    ranked = sorted(doc_map.values(), key=lambda d: d.combined_score, reverse=True)
    return ranked[:limit]
```

### 5.3 时间复杂度分析

设语义结果数为 $n$，关键词结果数为 $m$，元数据结果数为 $p$，合并后唯一文档数为 $k$。

| 操作 | 复杂度 | 说明 |
|------|--------|------|
| 语义结果聚合 | $O(n)$ | 哈希插入/查找平均 O(1) |
| 关键词结果聚合 | $O(m)$ | 同上 |
| 元数据结果聚合 | $O(p)$ | 同上 |
| 综合得分计算 | $O(k)$ | 遍历所有唯一文档 |
| 排序 | $O(k \log k)$ | Timsort |
| Top-K 切片 | $O(limit)$ | limit 通常很小（≤20） |

**总时间复杂度：$O(n + m + p + k \log k)$**

由于 $k \leq n + m + p$，最坏情况为 $O((n+m+p) \log (n+m+p))$。

### 5.4 空间复杂度分析

| 数据 | 空间 |
|------|------|
| 哈希表（doc_map） | $O(k)$ |
| 排序结果列表 | $O(k)$ |

**总空间复杂度：$O(k)$**

### 5.5 优化建议

| 优先级 | 优化方向 | 预期收益 | 实现复杂度 |
|--------|----------|----------|------------|

| **中** | 并行执行三路检索（ThreadPoolExecutor） | 三路独立，可并行降低延迟 | 低 |

## 6. 文档缓存查找 (_get_cached_or_parse)

### 6.1 算法描述

`_get_cached_or_parse()` 是文档解析的缓存层，避免对同一文件的重复解析。缓存键由 **文件路径 + 修改时间（mtime）** 组合而成，格式为 `"{path}:{mtime}"`。当文件内容未变化时（mtime 相同），直接返回缓存的解析结果；否则调用 Docling 重新解析并更新缓存。

该缓存使用模块级字典 `_DOCUMENT_CACHE` 实现，无大小限制，无淘汰策略。

### 6.2 伪代码

```
_DOCUMENT_CACHE = {}  # 模块级全局缓存

function _get_cached_or_parse(file_path):
    # 1. 获取文件修改时间
    stat = os.stat(file_path)
    mtime = stat.st_mtime

    # 2. 构造缓存键
    cache_key = f"{file_path}:{mtime}"

    # 3. 缓存查找（哈希表 O(1)）
    if cache_key in _DOCUMENT_CACHE:
        return _DOCUMENT_CACHE[cache_key]

    # 4. 缓存未命中，调用 Docling 解析
    document = docling_convert(file_path)

    # 5. 存入缓存
    _DOCUMENT_CACHE[cache_key] = document

    return document

function clear_document_cache():
    """清空缓存（用于测试或内存管理）"""
    _DOCUMENT_CACHE.clear()
```

### 6.3 时间复杂度分析

| 操作 | 复杂度 | 说明 |
|------|--------|------|
| `os.stat()` | $O(1)$ | 系统调用 |
| 缓存键构造 | $O(L)$ | L 为路径长度，通常 < 256 |
| 哈希表查找 | $O(1)$ 平均，$O(n)$ 最坏 | n 为缓存条目数 |
| 哈希表插入 | $O(1)$ 平均 | 同上 |
| Docling 解析（缓存未命中） | $O(p)$ | p 为文件大小相关 |

**总时间复杂度：$O(1)$ 平均**（缓存命中时）

### 6.4 空间复杂度分析

| 数据 | 空间 |
|------|------|
| 缓存字典 | $O(n \cdot avg\_doc\_size)$ |
| 单个缓存条目 | 与文档大小成正比 |

**总空间复杂度：$O(n)$**，$n$ 为缓存文档数。无上限，可能持续增长。

### 6.5 优化建议

| 优先级 | 优化方向 | 预期收益 | 实现复杂度 |
|--------|----------|----------|------------|
| **高** | 实现 LRU 淘汰策略（functools.lru_cache 或 cachetools.TTLCache） | 防止内存无限增长 | 低 |
| **高** | 设置缓存大小上限（如最多 100 个文档） | 控制内存占用 | 低 |
| **中** | 使用内容哈希（SHA256）替代 mtime | 检测内容变化更可靠 | 中 |
| **中** | 持久化缓存（磁盘/Redis） | 跨进程共享缓存 | 中 |
| **低** | 缓存统计（命中率、大小监控） | 可观测性 | 低 |

## 7. 稳定ID生成 (_stable_id)

### 7.1 算法描述

`_stable_id()` 用于为文档、语料库、文本块生成 **稳定且唯一** 的标识符。"稳定"意味着相同输入始终产生相同输出（幂等性），"唯一"意味着不同输入产生不同输出（低碰撞率）。

系统使用 **SHA1 哈希算法**，将输入字符串（通常是文件路径或内容摘要）转换为 40 位十六进制字符串。SHA1 的选择基于：
- 输出长度固定（160 位），适合作为数据库主键
- 碰撞概率极低（$2^{80}$ 安全强度）
- 计算速度快于 SHA256

### 7.2 伪代码

```
function _stable_id(*args):
    """基于多个参数的稳定ID生成"""
    # 1. 拼接所有参数为统一字符串
    content = "|".join(str(arg) for arg in args)

    # 2. 编码为 UTF-8 字节
    encoded = content.encode('utf-8')

    # 3. SHA1 哈希
    sha1_hash = hashlib.sha1(encoded).hexdigest()

    return sha1_hash

# 使用示例
corpus_id = _stable_id("corpus", folder_path)
doc_id = _stable_id("doc", file_path)
chunk_id = _stable_id("chunk", doc_id, chunk_position)
```

### 7.3 时间复杂度分析

设输入字符串总长度为 $n$。

| 操作 | 复杂度 | 说明 |
|------|--------|------|
| 字符串拼接 | $O(n)$ | join 操作 |
| UTF-8 编码 | $O(n)$ | 逐字符编码 |
| SHA1 哈希 | $O(n)$ | 分块处理，每块 64 字节 |

**总时间复杂度：$O(n)$**

### 7.4 空间复杂度分析

| 数据 | 空间 |
|------|------|
| 输入字符串 | $O(n)$ |
| 编码后字节 | $O(n)$ |
| SHA1 输出 | $O(1)$（固定 40 字符） |

**总空间复杂度：$O(n)$**（输入），**$O(1)$**（输出）

### 7.5 优化建议

| 优先级 | 优化方向 | 预期收益 | 实现复杂度 |
|--------|----------|----------|------------|
| **中** | 使用 xxHash 或 MurmurHash3 | 速度提升 5-10 倍（非加密场景无需 SHA1） | 低 |
| **中** | 截断输出（取前 16 字符） | 减少存储，碰撞风险仍可接受 | 低 |
| **低** | 缓存高频 ID（如 corpus_id） | 避免重复计算 | 低 |
| **低** | 使用 hashlib 的 usedforsecurity=False 标志 | 避免在某些受限环境中的安全策略问题 | 低 |

## 8. langextract实体聚合 (_aggregate_profile_metadata)

### 8.1 算法描述

`_aggregate_profile_metadata()` 负责将 langextract 库提取的原始实体列表转换为结构化的元数据字典。langextract 返回的每个实体包含：
- `extraction_class`：实体类型（如 `organization`、`person`、`deal_term`）
- `extraction_text`：实体文本值
- `attributes`：附加属性

聚合逻辑按 `extraction_class` 分组，然后根据配置的模式（mode）决定聚合方式：
- `list`：收集所有值到列表
- `count`：统计出现次数
- `boolean`：是否存在（has_X）
- `first`：取第一个值

### 8.2 伪代码

```
function _aggregate_profile_metadata(extractions, profile_config):
    """
    extractions: List[Extraction] — langextract 原始输出
    profile_config: Dict — 聚合配置
        {
            "organizations": {"class": "organization", "mode": "list"},
            "people_count": {"class": "person", "mode": "count"},
            "has_earnout": {"class": "earnout_clause", "mode": "boolean"}
        }
    """
    # 1. 按 extraction_class 分组
    grouped = {}  # class_name → List[Extraction]
    for ext in extractions:
        class_name = ext.extraction_class
        if class_name not in grouped:
            grouped[class_name] = []
        grouped[class_name].append(ext)

    # 2. 按配置模式聚合
    metadata = {}
    for field_name, config in profile_config.items():
        class_name = config["class"]
        mode = config["mode"]
        entities = grouped.get(class_name, [])

        if mode == "list":
            # 去重并保持顺序
            seen = set()
            values = []
            for ext in entities:
                val = ext.extraction_text.strip()
                if val and val not in seen:
                    seen.add(val)
                    values.append(val)
            metadata[f"lx_{field_name}"] = values

        elif mode == "count":
            metadata[f"lx_{field_name}"] = len(entities)

        elif mode == "boolean":
            metadata[f"lx_{field_name}"] = len(entities) > 0

        elif mode == "first":
            metadata[f"lx_{field_name}"] = entities[0].extraction_text if entities else None

    return metadata
```

### 8.3 时间复杂度分析

设提取实体数为 $e$，配置字段数为 $f$。

| 操作 | 复杂度 | 说明 |
|------|--------|------|
| 分组遍历 | $O(e)$ | 单遍扫描所有实体 |
| 聚合计算 | $O(f \cdot e_c)$ | $e_c$ 为每类实体数，$\sum e_c = e$ |
| 去重（set 查找） | $O(1)$ 平均 | 每值常数时间 |

**总时间复杂度：$O(e + f)$**

### 8.4 空间复杂度分析

| 数据 | 空间 |
|------|------|
| 分组字典 | $O(e)$ |
| 聚合结果 | $O(e)$（list 模式存储所有值） |
| 去重集合 | ≤ $O(e)$ |

**总空间复杂度：$O(e)$**

### 8.5 优化建议

| 优先级 | 优化方向 | 预期收益 | 实现复杂度 |
|--------|----------|----------|------------|
| **中** | 流式处理（不存储全量 extractions） | 降低峰值内存 | 中 |
| **中** | 使用 itertools.groupby 替代手动分组 | 代码更简洁 | 低 |

## 9. 查询词提取 (_query_terms)

### 9.1 算法描述

`_query_terms()` 从用户查询字符串中提取有意义的搜索词，用于关键词检索路径。处理流程：

1. **正则分词**：使用 `\w+` 或 `[a-zA-Z0-9_]+` 提取单词。
2. **长度过滤**：去除过短的词（如 "a", "is", "的"）。
3. **去重**：保持顺序去重。
4. **数量限制**：最多返回 8 个词（避免 SQL 参数过多）。

### 9.2 伪代码

```
function _query_terms(query, max_terms=8, min_length=2):
    """
    从查询字符串中提取搜索词
    """
    if not query or not query.strip():
        return []

    # 1. 正则分词
    words = re.findall(r'[a-zA-Z0-9_一-鿿]+', query.lower())

    # 2. 长度过滤 + 去重
    seen = set()
    terms = []
    for word in words:
        if len(word) >= min_length and word not in seen:
            seen.add(word)
            terms.append(word)
            if len(terms) >= max_terms:
                break

    return terms
```

### 9.3 时间复杂度分析

设查询字符串长度为 $n$。

| 操作 | 复杂度 | 说明 |
|------|--------|------|
| 正则匹配 | $O(n)$ | 单遍扫描 |
| 去重（set 查找） | $O(1) 平均 | 每词常数时间 |
| 截断 | $O(1) | 最多 8 个词 |

**总时间复杂度：$O(n)$**

### 9.4 空间复杂度分析

| 数据 | 空间 |
|------|------|
| 词列表 | $O(t)$，$t \leq 8$ |
| 去重集合 | $O(t)$ |

**总空间复杂度：$O(t)$**，$t$ 为词数（最多 8 个，即 $O(1)$）

## 10. 关键词搜索评分 (search_chunks)

### 10.1 算法描述

`search_chunks()` 是 DuckDB 存储层的关键词检索函数，基于 SQL `LIKE` 操作实现词项匹配。对于每个查询词，生成一个 `content LIKE '%word%'` 条件，然后统计每个 chunk 匹配的词数作为评分。

评分逻辑：
- 每个匹配的词贡献 1 分
- 多个词匹配可累加
- 按匹配词数降序排序

### 10.2 伪代码

```
function search_chunks(query_terms, limit=20):
    """
    关键词搜索评分
    """
    if not query_terms:
        return []

    # 1. 构建 SQL WHERE 条件
    conditions = []
    for term in query_terms:
        escaped = term.replace("'", "''")  # SQL 转义
        conditions.append(f"content LIKE '%{escaped}%'")

    where_clause = " OR ".join(conditions)

    # 2. 构建评分表达式（每个匹配词贡献 1 分）
    score_expr = " + ".join(
        f"(CASE WHEN content LIKE '%{term}%' THEN 1 ELSE 0 END)"
        for term in query_terms
    )

    # 3. 执行 SQL
    sql = f"""
        SELECT chunk_id, content, ({score_expr}) AS score
        FROM chunks
        WHERE {where_clause}
        ORDER BY score DESC
        LIMIT {limit}
    """

    results = duckdb.execute(sql).fetchall()

    return [SearchResult(chunk_id=row[0], content=row[1], score=row[2]) for row in results]
```

### 10.3 时间复杂度分析

设 chunk 数为 $n$，查询词数为 $t$。

| 操作 | 复杂度 | 说明 |
|------|--------|------|
| SQL 构建 | $O(t)$ | 拼接条件 |
| LIKE 匹配（单次） | $O(n \cdot c)$ | c 为平均 chunk 长度 |
| t 个词匹配 | $O(n \cdot c \cdot t)$ | 每个词扫描全表 |
| 排序 | $O(r \log r)$ | r 为匹配结果数 |

**总时间复杂度：$O(n \cdot c \cdot t + r \log r)$**

### 10.4 空间复杂度分析

| 数据 | 空间 |
|------|------|
| SQL 字符串 | $O(t)$ |
| 查询结果 | $O(r \cdot c)$ |

**总空间复杂度：$O(r)$**，$r$ 为结果数

### 10.5 优化建议

| 优先级 | 优化方向 | 预期收益 | 实现复杂度 |
|--------|----------|----------|------------|
| **高** | 使用 DuckDB FTS 全文索引扩展 | 从 $O(n)$ 降至 $O(\log n)$ 或更好 | 中 |

## 11. 引用提取 (extract_cited_sources)

### 11.1 算法描述

`extract_cited_sources()` 从 Agent 的最终答案中提取所有引用的源文件信息。系统强制要求 Agent 使用标准引用格式：

```
[Source: filename.pdf, Section 2.1]
[Source: agreement.docx]
```

提取逻辑：
1. 使用正则表达式匹配 `[Source: ...]` 模式。
2. 解析每个引用，提取文件名和可选的章节信息。
3. 保持顺序去重（同一文件多次引用只保留一次，但保留首次出现顺序）。

### 11.2 伪代码

```
function extract_cited_sources(final_answer):
    """
    从最终答案中提取引用源
    """
    if not final_answer:
        return []

    # 1. 正则匹配所有引用
    pattern = r'\[Source:\s*([^\]]+)\]'
    raw_citations = re.findall(pattern, final_answer)

    # 2. 解析并去重
    seen = set()
    sources = []

    for citation in raw_citations:
        # 解析 "filename, Section X" 格式
        parts = citation.split(",", 1)
        filename = parts[0].strip()
        section = parts[1].strip() if len(parts) > 1 else None

        if filename not in seen:
            seen.add(filename)
            sources.append(SourceReference(
                filename=filename,
                section=section
            ))

    return sources
```

设最终答案长度为 $n$，引用数为 $s$。

## 12. 条件分割状态机 (_split_conditions)

### 12.1 算法描述

`_split_conditions()` 是 DSL 解析器的核心组件，实现了一个 **手写的手动下降解析器（recursive descent parser）**，通过跟踪嵌套深度来正确分割顶层逗号分隔的条件。

状态机维护以下状态：
- `depth_paren`：小括号 `()` 嵌套深度
- `depth_bracket`：中括号 `[]` 嵌套深度
- `in_quote`：当前是否在引号内（记录引号字符）

只有当 `depth_paren == 0 && depth_bracket == 0 && not in_quote` 时，逗号才被视为顶层分隔符。

### 12.2 伪代码

```
function _split_conditions(text):
    """
    状态机实现的条件分割
    """
    conditions = []
    current = []  # 字符缓冲区
    state = {
        "depth_paren": 0,
        "depth_bracket": 0,
        "in_quote": None  # None, "'", '"'
    }

    for char in text:
        if state["in_quote"]:
            # 在引号内：只关注闭合引号
            current.append(char)
            if char == state["in_quote"]:
                state["in_quote"] = None

        elif char in ("'", '"'):
            # 进入引号
            state["in_quote"] = char
            current.append(char)

        elif char == '(':
            state["depth_paren"] += 1
            current.append(char)

        elif char == ')':
            state["depth_paren"] -= 1
            current.append(char)

        elif char == '[':
            state["depth_bracket"] += 1
            current.append(char)

        elif char == ']':
            state["depth_bracket"] -= 1
            current.append(char)

        elif char == ',' and is_top_level(state):
            # 顶层逗号：分割条件
            conditions.append(''.join(current))
            current = []

        else:
            current.append(char)

    # 处理最后一个条件
    if current:
        conditions.append(''.join(current))

    return conditions

function is_top_level(state):
    return (state["depth_paren"] == 0 and
            state["depth_bracket"] == 0 and
            state["in_quote"] is None)
```

### 12.3 时间复杂度分析

设字符串长度为 $n$。

| 操作 | 复杂度 | 说明 |
|------|--------|------|
| 单字符处理 | $O(1)$ | 常数时间状态更新 |
| 完整遍历 | $O(n)$ | 每个字符处理一次 |
| 字符串拼接 | $O(n)$ | join 操作 |

**总时间复杂度：$O(n)$**

### 12.4 空间复杂度分析

| 数据 | 空间 |
|------|------|
| 状态变量 | $O(1)$ |
| 当前条件缓冲区 | $O(L_max) ⊆ O(n)$ |
| 结果列表 | $O(n)$ |

**总空间复杂度：$O(n)$**

### 12.5 优化建议

| 优先级 | 优化方向 | 预期收益 | 实现复杂度 |
|--------|----------|----------|------------|
| **高** | 使用正式解析器生成器（lark / pyparsing） | 更健壮、可扩展、易维护 | 中 |
| **中** | 支持转义字符（`\'`、`\"`） | 处理包含引号的值 | 低 |
| **中** | 错误恢复与定位（报告具体出错位置） | 更好的错误提示 | 中 |

## 13. 语义搜索 (search_chunks_semantic)

### 13.1 算法描述

`search_chunks_semantic()` 是基于向量嵌入的语义检索函数，使用 DuckDB 的 `array_cosine_similarity()` 函数计算查询向量与存储 chunk 向量之间的余弦相似度。

检索流程：
1. **查询嵌入**：调用 EmbeddingProvider 将查询文本转换为向量。
2. **相似度计算**：在 DuckDB 中执行 `array_cosine_similarity(query_embedding, chunk_embedding)`。
3. **排序返回**：按相似度降序返回 Top-K 结果。

DuckDB 支持两种执行模式：
- **线性扫描**：全表计算相似度，$O(n)$
- **HNSW 索引**：使用 Hierarchical Navigable Small World 近似最近邻索引，$O(\log n)$

### 13.2 伪代码

```
function search_chunks_semantic(query_text, query_embedding=None, limit=10):
    """
    语义搜索
    """
    # 1. 获取查询向量
    if query_embedding is None:
        query_embedding = embedding_provider.embed_query(query_text)

    # 2. 转换为 DuckDB 向量字面量
    vector_literal = "[" + ",".join(str(v) for v in query_embedding) + "]"

    # 3. 执行相似度查询
    sql = f"""
        SELECT chunk_id, content, chunk_text,
               array_cosine_similarity(embedding, {vector_literal}) AS similarity
        FROM chunks
        WHERE embedding IS NOT NULL
        ORDER BY similarity DESC
        LIMIT {limit}
    """

    # 4. 如果使用 HNSW 索引：
    -- CREATE INDEX idx_embedding ON chunks USING HNSW(embedding);
    -- DuckDB 会自动使用索引加速 ORDER BY + LIMIT

    results = duckdb.execute(sql).fetchall()

    return [
        SemanticResult(
            chunk_id=row[0],
            content=row[1],
            score=row[3]
        )
        for row in results
    ]
```

### 13.3 时间复杂度分析

设 chunk 数为 $n$，嵌入维度为 $d$（通常为 768 或 1536）。

| 模式 | 复杂度 | 说明 |
|------|--------|------|
| 线性扫描 | $O(n \cdot d)$ | 每个 chunk 计算 d 维点积 |
| HNSW 索引 | $O(\log n \cdot d)$ | 近似最近邻搜索 |
| 排序 | $O(n \log n)$ 或 $O(limit \cdot log n) | 全排序 vs Top-K |

**总时间复杂度：**
- 无索引：$O(n \cdot d + n \log n)$
- 有 HNSW 索引：$O(\log n \cdot d)$

### 13.4 空间复杂度分析

| 数据 | 空间 |
|------|------|
| 嵌入向量表 | $O(n \cdot d)$ |
| HNSW 索引 | $O(n \cdot d \cdot M)$（M 为 HNSW 连接数，通常 16） |
| 查询结果 | $O(limit \cdot d)$ |

**总空间复杂度：$O(n \cdot d)$**

### 13.5 优化建议

| 优先级 | 优化方向 | 预期收益 | 实现复杂度 |
|--------|----------|----------|------------|
| **高** | 确保 HNSW 索引创建和使用 | 从 $O(n)$ 降至 $O(\log n)$ | 低 |
| **高** | 使用 ANN 库（FAISS、Annoy、ScaNN） | 更高性能的近似搜索 | 中 |
| **中** | 嵌入维度降维（PCA） | 减少存储和计算 | 中 |
| **中** | 量化（PQ、SQ8） | 减少内存占用 | 中 |
| **低** | 查询结果缓存 | 重复查询加速 | 低 |
| **低** | 批量嵌入计算 | 提高吞吐量 | 低 |
