**文件**：`src/sirchmunk/agentic/react_agent.py` → `ReActSearchAgent`

    ├── SearchContext(max_token_budget, max_loops)  # 创建上下文

**关键决策点**：
1. `_parse_tool_call` 支持多种格式（JSON/函数调用），容错性强
2. nudge 机制优雅处理 LLM 不遵从指令
3. 结果截断防止单次工具返回撑爆预算

**走读路径**：

    ├── self.llm = llm
    ├── self.storage = KnowledgeStorage(work_path)
    └── self.embedding_util = EmbeddingUtil()

    ├── clusters = storage.list_clusters()       # 加载所有簇
    │
    ├── Phase 1: Connect & Merge
    │   ├── if new_count >= 5:
    │   │   ├── similarity = cosine(emb1, emb2)
    │   │   ├── if sim > 0.60: add_edge()
    │   │   └── if sim > 0.90: merge_clusters()
    │   └── update storage
    │
    ├── Phase 2: Edge Refresh
    │   └── if refresh_count >= threshold:
    │       └── recompute_edge_weights()
    │
    ├── Phase 3: Meta Cluster Detection
    │   └── if step_interval AND cluster_change:
    │       ├── graph = build_igraph(clusters)
    │       ├── communities = leidenalg.find_partition(graph)

2. Leiden 算法优于 Louvain 的收敛性
3. 弱语义边（统计）与 RichSemanticEdge（语义）双层设计

    ├── _run_extraction_in_child(file_path, profile_dict)

## 10.3 架构决策记录（ADR）

### ADR-001：选择 ripgrep-all 而非向量数据库

**状态**：已接受

**背景**：
传统 RAG 系统依赖向量数据库进行语义检索，但存在索引构建成本高、数据更新滞后、精度损失等问题。

**决策**：
使用 ripgrep-all (rga) 作为主要检索引擎，直接对原始文件进行全文检索。

**理由**：
1. 零索引成本：无需预处理，即搜即用
2. 实时性：数据变化立即反映在搜索结果中
3. 确定性：精确匹配而非近似匹配
4. 资源效率：极低 RAM/CPU 消耗
5. 多格式支持：100+ 文件格式

**后果**：
- 正面：部署简单、成本低、精度高
- 负面：语义理解能力弱于向量检索（通过 LLM 推理补偿）

---

### ADR-002：选择 ReAct Agent 范式

**状态**：已接受

**背景**：
搜索场景复杂多变，固定管线难以适应所有查询类型。

**决策**：
采用 ReAct（Reasoning + Acting）Agent 范式，让 LLM 自主决定检索策略。

**理由**：
1. 灵活性：根据查询复杂度动态调整检索深度
2. 自适应：能处理从简单关键词到复杂推理的各种查询
3. 可解释：推理过程可见（通过消息历史）

**后果**：
- 正面：适应性强、用户体验好
- 负面：延迟较高（多轮 LLM 调用）、成本不可控

---

### ADR-003：选择 DuckDB 作为持久化存储

**状态**：已接受

**背景**：
需要嵌入式数据库存储会话和消息历史，同时要求零运维。

**决策**：
使用 DuckDB 嵌入式 OLAP 数据库。

**理由**：
1. 嵌入式：无需独立数据库进程
2. OLAP 优化：分析查询性能好
3. 零运维：自动备份、自动优化
4. 单文件：数据文件可移植

**后果**：
- 正面：部署简单、性能好
- 负面：多进程写入需要特殊处理（Persist 模式解决）

---

### ADR-004：知识表示使用 KnowledgeCluster 图谱

**状态**：已接受

**背景**：
搜索结果需要结构化表示，支持推理和进化。

**决策**：
使用 KnowledgeCluster 作为核心知识单元，构建知识图谱。

**理由**：
1. 可追溯性：每个知识声明链接到原始证据
2. 可进化：支持合并、连接、生命周期管理
3. 可推理：支持语义边和认知导航

**后果**：
- 正面：知识积累价值、越用越聪明
- 负面：实现复杂度高、存储开销

---

### ADR-005：前端使用 Next.js 静态导出

**状态**：已接受

**背景**：
前端需要与后端 API 配合部署，同时支持开发模式热更新。

3. 开发模式：支持 `npm run dev` 热更新
4. React 生态：组件丰富、社区活跃

**后果**：
- 正面：部署简单、开发体验好
- 负面：静态导出限制（无 SSR）

## 10.4 关键算法分析

### 10.4.1 蒙特卡洛证据采样

**伪代码**：
```
function MonteCarloEvidenceSampling(search_results, query, max_iterations):
    evidences = []
    for iteration in 1..max_iterations:
        # 1. ROI 定位
        roi = locate_roi(search_results, query)
        
        # 2. 随机采样
        sample = random_sample(roi, sample_size=1000)
        
        # 3. 证据验证
        for snippet in sample:
            is_relevant = llm_verify(snippet, query)
            if is_relevant:
                evidences.append(EvidenceUnit(
                    doc_id=snippet.doc_id,
                    file_or_url=snippet.path,
                    summary=snippet.text,
                    is_found=True,
                    snippets=[snippet.to_dict()]
                ))
        
        # 4. 收敛检查
        if evidences.confidence > threshold:
            break
    
    return evidences
```

**时间复杂度**：
- 最坏情况：O(N × M × L)，N=迭代次数，M=平均 ROI 大小，L=LLM 推理延迟
- 平均情况：O(K × L)，K=收敛所需证据数

**空间复杂度**：O(K × S)，K=证据数，S=平均证据大小

**优化建议**：
1. 使用重要性采样替代纯随机采样
2. 缓存 LLM 验证结果避免重复调用
3. 并行验证多个 snippet

### 10.4.2 SummaryIndex 嵌入 + BM25 融合

**伪代码**：
```
function SummaryIndex.search(query, top_k=10):
    # 1. 计算查询嵌入
    query_embedding = embed(query)  # 384-dim
    
    # 2. 双通道评分
    for entry in entries:
        # 嵌入通道
        emb_score = cosine(query_embedding, entry.embedding)
        
        # BM25 通道
        bm25_score = 0
        for token in segment(query):
            idf = log((N - df[token] + 0.5) / (df[token] + 0.5))
            tf = entry.token_freqs.get(token, 0)
            bm25_score += idf * (tf * (k1 + 1)) / (tf + k1 * (1 - b + b * len(entry.tokens) / avg_len))
        
        entry.emb_scores.append(emb_score)
        entry.bm25_scores.append(bm25_score)
    
    # 3. Z-Score 归一化
    emb_z = z_score(entry.emb_scores)
    bm25_z = z_score(entry.bm25_scores)
    
    # 4. 加权融合 + Sigmoid
    for entry in entries:
        entry.final_score = sigmoid(alpha * emb_z[entry] + (1-alpha) * bm25_z[entry])
    
    # 5. Top-K 排序
    return sorted(entries, key=final_score, reverse=True)[:top_k]
```

**时间复杂度**：
- 嵌入计算：O(D)，D=嵌入维度（384）
- BM25 计算：O(N × T)，N=文档数，T=查询词数
- 总复杂度：O(N × T + N log N)（排序）

**空间复杂度**：O(N × (D + V))，D=嵌入维度，V=词表大小

**优化建议**：
1. 使用 FAISS 加速嵌入相似度计算
2. 预计算 IDF 值
3. 使用倒排索引加速 BM25

### 10.4.3 Leiden 社区发现（知识进化）

**伪代码**：
```
function detect_meta_clusters(clusters, edges):
    # 1. 构建图
    graph = igraph.Graph()
    graph.add_vertices(len(clusters))
    graph.add_edges([(e.source, e.target) for e in edges])
    graph.vs["name"] = [c.id for c in clusters]
    graph.es["weight"] = [e.weight for e in edges]
    
    # 2. Leiden 算法
    partition = leidenalg.find_partition(
        graph,
        leidenalg.ModularityVertexPartition,
        weights="weight",
        n_iterations=10
    )
    
    # 3. 创建 Meta 簇
    meta_clusters = []
    for community in partition:
        meta = KnowledgeCluster(
            id=generate_id(),
            name=llm_generate_name(community),
            lifecycle=Lifecycle.META,
            related_clusters=[clusters[i].id for i in community]
        )
        meta_clusters.append(meta)
    
    return meta_clusters
```

**时间复杂度**：
- Leiden 算法：O(N × log N)，N=节点数
- 实际运行：通常 < 1s（N < 1000）

**空间复杂度**：O(N + E)，E=边数

**优化建议**：
1. 使用增量 Leiden 算法（仅更新变化部分）
2. 缓存图结构避免重复构建

function persist_sync(db, target_path):
    # 1. 写入临时文件
    temp_path = target_path + ".tmp_duckdb"
    db.execute(f"EXPORT DATABASE '{temp_path}'")
    
    # 2. 原子替换
