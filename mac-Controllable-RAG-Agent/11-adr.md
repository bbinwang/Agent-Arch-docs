## 11.1 ADR 概述

架构决策记录 (ADR) 是一种记录软件项目中重要架构决策的方法论。每个 ADR 包含：

- **标题**: 决策的简短描述
- **状态**: 提议/接受/废弃/替代
- **背景**: 决策的上下文和约束
- **决策**: 最终选择的方案
- **理由**: 为什么选择这个方案
- **后果**: 决策带来的正面和负面影响
- **替代方案**: 考虑过但未选择的方案

## 11.2 ADR-001: 采用 Plan-and-Execute 模式

### 状态
✅ **接受** (Accepted)

### 背景

项目需要解决**复杂多跳推理问题**，例如：
> "帮助反派的那位教授教的是什么课？"

这类问题需要：
1. 识别反派是谁
2. 识别帮助反派的人
3. 识别该人教授的課程

传统的单步 RAG（检索→生成）无法处理此类问题，因为：
- 单次检索无法覆盖所有必要信息
- 需要中间推理步骤
- 需要动态决定下一步做什么

### 决策

采用 **Plan-and-Execute** 模式作为 Agent 的核心架构：

```
问题 → 计划生成 → 步骤1执行 → 步骤2执行 → ... → 最终答案
         ↑                                      |
         └────────── 动态重规划 ←────────────────┘
```

### 理由

| 优势 | 说明 |
|------|------|
| **可解释性** | 每个步骤清晰可见，便于调试 |
| **可控性** | 可以人工干预计划或执行 |
| **灵活性** | 支持动态重规划，适应新信息 |
| **可组合** | 步骤可以复用和重新排序 |

### 后果

| 正面 | 负面 |
|------|------|
| ✅ 解决复杂问题 | ❌ 延迟增加（多步执行） |
| ✅ 执行过程透明 | ❌ LLM 调用次数增加 |
| ✅ 易于调试 | ❌ 计划可能不准确 |
| ✅ 支持人工干预 | ❌ 重规划可能循环 |

### 替代方案

| 方案 | 描述 | 未选择原因 |
|------|------|-----------|
| **ReAct** | 单步推理+动作交替 | 缺乏全局规划，可能陷入局部最优 |
| **BabyAGI** | 任务驱动的自主任务创建 | 过于复杂，难以控制 |
| **Chain-of-Thought** | 单步链式推理 | 无法处理需要多源信息的问题 |
| **Self-RAG** | 自我反思的检索 | 仅支持单步检索，不支持多步计划 |

### 相关论文

- [Plan-and-Solve Prompting](https://arxiv.org/abs/2305.04091) (2023)
- [BabyAGI](https://github.com/yoheinakajima/babyagi) (2023)
- [Self-RAG](https://arxiv.org/abs/2310.11511) (2023)

## 11.3 ADR-002: 使用 LangGraph 作为编排引擎

### 状态
✅ **接受** (Accepted)

### 背景

Plan-and-Execute 模式需要一个**编排引擎**来管理：
- 节点（步骤）的执行顺序
- 条件分支（根据结果选择下一步）
- 循环（重规划、重新生成）
- 状态传递（步骤间共享数据）

### 决策

选择 **LangGraph** 作为编排引擎，基于以下特性：

```python
from langgraph.graph import StateGraph

workflow = StateGraph(PlanExecute)
workflow.add_node("step1", step1_function)
workflow.add_conditional_edges("step1", condition_function, {
    "result_a": "step2a",
    "result_b": "step2b"
})
app = workflow.compile()
```

### 理由

| 优势 | 说明 |
|------|------|
| **状态图范式** | 天然匹配 Agent 的"节点-边-状态"模型 |
| **LangChain 集成** | 与现有 Chain 无缝集成 |
| **可视化** | 可导出 Mermaid 图，便于理解 |
| **流式输出** | 支持 `stream()` 实时推送状态 |
| **条件分支** | `add_conditional_edges()` 支持动态路由 |
| **循环支持** | 图内循环（重规划）原生支持 |

### 后果

| 正面 | 负面 |
|------|------|
| ✅ 声明式图定义 | ❌ 学习曲线（需理解状态图概念） |
| ✅ 可视化友好 | ❌ 版本 0.0.49 较新，API 可能变化 |
| ✅ 流式输出 | ❌ 调试复杂图较困难 |
| ✅ 条件分支 | ❌ 循环可能导致无限执行 |

### 替代方案

| 方案 | 描述 | 未选择原因 |
|------|------|-----------|
| **LangChain Agent** | 内置 Agent 抽象 | 不够灵活，难以实现复杂图 |
| **AutoGen** | 多 Agent 对话框架 | 过于重量级，不适合单 Agent |
| **自定义状态机** | 手写状态机逻辑 | 开发成本高，维护困难 |
| **Prefect/Dagster** | 工作流编排 | 面向数据管道，不适合 LLM 编排 |

## 11.4 ADR-003: 使用 FAISS 作为向量存储

### 状态
✅ **接受** (Accepted)

### 背景

RAG 系统需要存储和检索文档的向量嵌入。选择向量存储需要考虑：
- 数据规模（当前 ~1200 个文档）
- 部署复杂度（是否需要外部服务）
- 性能要求（检索延迟）
- 持久化需求

### 决策

选择 **FAISS (Facebook AI Similarity Search)** 作为向量存储：

```python
from langchain.vectorstores import FAISS

# 创建索引
vectorstore = FAISS.from_documents(documents, embeddings)

# 持久化
vectorstore.save_local("chunks_vector_store")

# 加载
vectorstore = FAISS.load_local("chunks_vector_store", embeddings)
```

### 理由

| 优势 | 说明 |
|------|------|
| **本地优先** | 无需外部服务，单机即可运行 |
| **零配置** | 无需安装数据库，文件即存储 |
| **性能优秀** | 对小规模数据（<100万）检索极快 |
| **LangChain 集成** | 原生支持 `as_retriever()` |
| **持久化简单** | `save_local()` / `load_local()` |

### 后果

| 正面 | 负面 |
|------|------|
| ✅ 零配置部署 | ❌ 不支持分布式 |
| ✅ 检索速度快 | ❌ 不支持元数据过滤 |
| ✅ 文件持久化 | ❌ 索引文件可能较大 |
| ✅ 易于备份 | ❌ 不支持并发写入 |

### 替代方案

| 方案 | 描述 | 未选择原因 |
|------|------|-----------|
| **Qdrant** | 高性能向量数据库 | 需要外部服务 |
| **Milvus** | 分布式向量数据库 | 过于重量级 |
| **Pinecone** | 托管向量服务 | 需要网络，有成本 |
| **ChromaDB** | 轻量级向量存储 | 当时集成不如 FAISS 成熟 |

## 11.5 ADR-004: 采用命名实体匿名化

### 状态
✅ **接受** (Accepted)

### 背景

LLM（如 GPT-4o）在预训练中"知道"大量事实。当问题包含已知实体（如 "Harry Potter"）时，LLM 可能：
1. 基于参数知识而非检索数据制定计划
2. 生成看似正确但实际基于先验的答案
3. 无法验证是否真正依赖检索数据

### 决策

在计划生成前，将问题中的**命名实体替换为变量**：

```
原始: "how did harry beat quirrell?"
匿名: "how did X beat Y?"
映射: {"X": "harry", "Y": "quirrell"}
```

计划生成后，再将变量替换回原始实体。

### 理由

| 优势 | 说明 |
|------|------|
| **消除先验偏见** | LLM 不知道 "X" 是谁，只能基于问题结构制定计划 |
| **通用性** | 匿名化后的计划可应用于不同领域的同名实体 |
| **可验证性** | 可以明确区分"LLM 知道什么"和"数据说了什么" |
| **教学价值** | 展示如何控制 LLM 的参数知识影响 |

### 后果

| 正面 | 负面 |
|------|------|
| ✅ 减少先验影响 | ❌ 可能丢失语义（如 "the Chosen One" → "the X"） |
| ✅ 提高计划通用性 | ❌ 实体识别可能错误 |
| ✅ 便于验证 | ❌ 增加一次 LLM 调用 |
| ✅ 教学价值 | ❌ 去匿名化可能引入错误 |

### 替代方案

| 方案 | 描述 | 未选择原因 |
|------|------|-----------|
| **直接提问** | 不匿名化 | LLM 会基于先验知识 |
| **负向提示** | Prompt 中要求"不要使用先验知识" | 不可靠，LLM 难以遵守 |
| **检索增强** | 先检索再提问 | 无法解决计划阶段的先验问题 |
| **微调** | 微调 LLM 不依赖先验 | 成本过高 |

## 11.6 ADR-005: 采用三路异构检索

### 状态
✅ **接受** (Accepted)

### 背景

不同类型的查询需要不同粒度的信息：

| 查询类型 | 需要的信息 | 最佳来源 |
|----------|-----------|----------|
| "Harry 说了什么？" | 原文引文 | Quotes |
| "第一章讲了什么？" | 章节概要 | Summaries |
| "Harry 怎么打败 Quirrell？" | 详细描述 | Chunks |

单一检索源无法满足所有需求。

### 决策

采用**三路异构向量存储**：

| 存储 | 内容 | k 值 | 用途 |
|------|------|------|------|
| **chunks_vector_store** | 1000 字符文本块 | 1 | 详细事实检索 |
| **chapter_summaries_vector_store** | 章节摘要 | 1 | 宏观理解 |
| **book_quotes_vectorstore** | 原文引文 | 10 | 精确引文 |

### 理由

| 优势 | 说明 |
|------|------|
| **多粒度覆盖** | 细节/摘要/引文互补 |
| **灵活路由** | TaskHandler 根据任务类型选择 |
| **高精度** | 不同类型查询使用最合适的源 |
| **可解释性** | 可以追溯答案来自哪个源 |

### 后果

| 正面 | 负面 |
|------|------|
| ✅ 覆盖多种查询 | ❌ 需要维护 3 个索引 |
| ✅ 提高检索精度 | ❌ 增加存储和内存 |
| ✅ 灵活路由 | ❌ 路由决策可能错误 |
| ✅ 可解释性 | ❌ 需要 3 次嵌入调用（编码时） |

### 替代方案

| 方案 | 描述 | 未选择原因 |
|------|------|-----------|
| **单一索引** | 所有数据混在一个索引 | 粒度不匹配 |
| **混合检索** | BM25 + 向量检索 | 增加复杂度 |
| **重排序** | 单一检索 + 重排序 | 无法解决粒度问题 |
| **多索引路由** | 更多索引类型 | 当前 3 种已足够 |

## 11.7 ADR-006: 采用多层幻觉防控

### 状态
✅ **接受** (Accepted)

### 背景

LLM 幻觉（Hallucination）是 RAG 系统的核心挑战。本项目设计了**三层幻觉防控**：

```
Layer 1: 蒸馏验证 (is_distilled_content_grounded_on_content)
    ↓
Layer 2: 答案幻觉检测 (is_answer_grounded_on_context)
    ↓
Layer 3: CoT 负例 (Example 3: "there is no way to determine")
```

### 决策

采用**多层验证**而非单一检查点：

| 层级 | 检查内容 | 失败处理 |
|------|----------|----------|
| **L1: 蒸馏验证** | 蒸馏内容是否基于原始检索 | 重新蒸馏（循环） |
| **L2: 答案验证** | 答案是否基于上下文 | 重新生成（循环） |
| **L3: CoT 负例** | 教会模型"不知道就说不知道" | 拒绝回答 |

### 理由

| 优势 | 说明 |
|------|------|
| **深度防御** | 多层检查，单层失败仍有其他层 |
| **不同类型幻觉** | 每层针对不同幻觉类型 |
| **可追溯** | 可以定位哪层发现问题 |
| **教学价值** | 展示幻觉防控的最佳实践 |

### 后果

| 正面 | 负面 |
|------|------|
| ✅ 高准确性 | ❌ 多次 LLM 调用增加成本 |
| ✅ 可追溯 | ❌ 循环可能无限 |
| ✅ 教学价值 | ❌ 延迟增加 |
| ✅ 深度防御 | ❌ 每层都有误判可能 |

### 替代方案

| 方案 | 描述 | 未选择原因 |
|------|------|-----------|
| **单一检查** | 仅检查最终答案 | 不够全面 |
| **NLI 模型** | 使用专门 NLI 模型 | 增加依赖，可能不如 LLM 准确 |
| **人工审核** | 人工检查每个答案 | 不可扩展 |
| **Self-Consistency** | 多次生成取一致 | 成本高，不一定有效 |

### 相关论文

- [Self-RAG: Learning to Retrieve, Generate, and Critique through Self-Reflection](https://arxiv.org/abs/2310.11511) (2023)
- [CRITIC: Large Language Models Can Self-Correct with Tool-Interactive Critiquing](https://arxiv.org/abs/2305.11738) (2023)

## 11.8 ADR-007: 使用 Streamlit 作为前端

### 状态
✅ **接受** (Accepted)

### 背景

项目需要一个**实时可视化界面**来展示 Agent 的执行过程。前端选择需要考虑：
- 开发速度（原型 vs 生产）
- 与 Python 后端的集成
- 实时更新能力
- 图可视化支持

### 决策

选择 **Streamlit** 作为前端框架：

```python
import streamlit as st

st.title("Real-Time Agent Execution Visualization")
question = st.text_input("Enter your question:")
if st.button("Run Agent"):
    for output in app.stream(inputs):
        st.write(output)
```

### 理由

| 优势 | 说明 |
|------|------|
| **快速原型** | 几行代码即可创建交互式 UI |
| **原生 Python** | 与 Agent 代码同语言，无缝集成 |
| **状态管理** | `st.session_state` 天然适合 Agent 状态 |
| **组件生态** | `pyvis` + `components.html` 实现图可视化 |
| **热重载** | 代码修改自动刷新 |

### 后果

| 正面 | 负面 |
|------|------|
| ✅ 开发快速 | ❌ 不适合高并发 |
| ✅ Python 原生 | ❌ 前端交互有限 |
| ✅ 实时更新 | ❌ 无复杂路由 |
| ✅ 易于部署 | ❌ 定制化受限 |

### 替代方案

| 方案 | 描述 | 未选择原因 |
|------|------|-----------|
| **Flask + React** | 前后端分离 | 开发成本高 |
| **Gradio** | ML 专用 UI | 定制化受限 |
| **Dash** | Plotly 生态 | 学习曲线 |
| **FastAPI + Vue** | 现代全栈 | 过于重量级 |

## 11.9 ADR-008: 使用 TypedDict 管理状态

### 状态
✅ **接受** (Accepted)

### 背景

LangGraph 图节点间需要传递状态。状态管理方式影响：
- 类型安全
- 序列化
- 可扩展性
- 调试便利性

### 决策

使用 **TypedDict** 定义状态对象：

```python
class PlanExecute(TypedDict):
    curr_state: str
    question: str
    anonymized_question: str
    # ... 更多字段
```

### 理由

| 优势 | 说明 |
|------|------|
| **LangGraph 兼容** | StateGraph 直接支持 TypedDict |
| **类型安全** | mypy 可以验证字段类型 |
| **灵活性** | 字段可以动态扩展 |
| **序列化友好** | TypedDict 本质是 dict，易于 JSON 序列化 |

### 后果

| 正面 | 负面 |
|------|------|
| ✅ 类型安全 | ❌ 无运行时校验 |
| ✅ 灵活性 | ❌ 字段可能缺失 |
| ✅ 序列化友好 | ❌ 无默认值支持 |

### 替代方案

| 方案 | 描述 | 未选择原因 |
|------|------|-----------|
| **dataclass** | Python 标准数据类 | LangGraph 支持不如 TypedDict |
| **Pydantic BaseModel** | 运行时校验 | 序列化稍复杂 |
| **普通 dict** | 无类型 | 无类型安全 |
| **NamedTuple** | 不可变 | 无法修改字段 |

## 11.10 ADR-009: 使用 LCEL 构建 Chain

### 状态
✅ **接受** (Accepted)

### 背景

LLM 调用需要组合多个组件（Prompt、LLM、Parser）。组合方式影响：
- 可读性
- 可测试性
- 可替换性
- 流式支持

### 决策

使用 **LCEL (LangChain Expression Language)** 声明式构建 Chain：

```python
chain = prompt | llm.with_structured_output(OutputSchema)
```

### 理由

| 优势 | 说明 |
|------|------|
| **声明式** | 描述"做什么"而非"怎么做" |
| **可组合** | Chain 可以嵌套 |
| **可流式** | 天然支持 `stream()` |
| **可替换** | 可以轻松更换组件 |

### 后果

| 正面 | 负面 |
|------|------|
| ✅ 声明式 | ❌ 调试稍困难 |
| ✅ 可组合 | ❌ 学习曲线 |
| ✅ 可流式 | ❌ 复杂 Chain 可读性下降 |

### 替代方案

| 方案 | 描述 | 未选择原因 |
|------|------|-----------|
| **LLMChain** | 旧版 API | 已被 LCEL 替代 |
| **手动编排** | 手写调用逻辑 | 代码冗长 |
| **Pipeline 类** | 自定义 Pipeline | 重复造轮子 |
