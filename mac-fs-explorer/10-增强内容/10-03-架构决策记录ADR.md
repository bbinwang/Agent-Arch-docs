## ADR-001: 选择事件驱动工作流架构

### 状态: 已接受

### 背景

Agent 决策循环需要一个清晰的编排机制，支持状态管理、事件传播和人机交互。

### 决策

采用 `llama-index-workflows` 框架实现事件驱动的工作流架构。

### 理由

1. **状态隔离**: 每个步骤无状态，状态通过 Context 集中管理
2. **事件溯源**: 所有中间事件可被观察和记录
3. **人机协作**: InputRequiredEvent/HumanResponseEvent 天然支持 Human-in-the-Loop
4. **可扩展性**: 新增步骤不影响现有代码

### 后果

- ✅ 清晰的步骤边界
- ✅ 良好的可观测性
- ⚠️ 代码重复（四个步骤的事件路由逻辑相同）

## ADR-002: 选择 Gemini 作为 Agent 决策模型

### 状态: 已接受

### 背景

Agent 需要一个能够理解自然语言任务、做出决策、调用工具的 LLM。

### 决策

选择 Google Gemini（gemini-3-flash-preview）作为 Agent 决策模型。

### 理由

1. **结构化输出**: 支持 `response_json_schema` 直接输出符合 Schema 的 JSON
2. **长上下文**: 支持大上下文窗口，适合包含文件内容的对话历史
3. **成本效益**: Flash 模型快速且经济
4. **异步支持**: `google-genai` SDK 提供良好的异步支持

### 后果

- ✅ 结构化输出减少解析错误
- ✅ Flash 模型降低延迟和成本
- ⚠️ 依赖 Google Cloud 服务

## ADR-003: 选择混合检索（Dense + Sparse + RRF）

### 状态: 已接受

### 背景

传统 RAG 需要高精度检索，单一检索方式有局限性。

### 决策

结合 Dense（OpenAI Embedding）和 Sparse（BM25）检索，使用 RRF 融合结果。

### 理由

1. **互补性**: Dense 擅长语义匹配，Sparse 擅长关键词匹配
2. **RRF 优势**: 无需训练，无监督融合多路结果
3. **经验验证**: k=60 是文献推荐的默认值

### 后果

- ✅ 检索精度提升
- ⚠️ 需要维护两套嵌入
- ⚠️ 存储成本增加

## ADR-004: 使用 DiskCache 作为持久缓存

### 状态: 已接受

### 背景

LlamaParse 解析结果需要缓存以避免重复 API 调用。

### 决策

使用 `diskcache`（SQLite 后端）作为持久缓存。

### 理由

1. **零配置**: 无需额外服务进程
2. **持久化**: 数据在重启后仍保留
3. **SQLite 可靠**: 经过广泛验证的数据库引擎
4. **简单性**: 键值缓存无需复杂数据结构

### 后果

- ✅ 开箱即用
- ✅ 跨会话持久化
- ⚠️ 无自动过期策略

## ADR-005: 使用 Monorepo + uv workspace

### 状态: 已接受

### 背景

项目包含多个相互关联的包，需要统一管理。

### 决策

使用 Monorepo 结构，通过 `uv workspace` 管理多包依赖。

### 理由

1. **代码复用**: fs-explorer 和 rag-starterkit 共享缓存机制
2. **独立发布**: 每个包有独立的 pyproject.toml
3. **统一工具链**: 根目录的 Makefile 统一管理所有包
4. **依赖解析**: uv 自动处理跨包依赖

### 后果

- ✅ 统一的依赖管理
- ✅ 简化的开发流程
- ⚠️ 构建时间增加

## ADR-006: 使用 Pydantic 作为数据模型层

### 状态: 已接受

### 背景

需要类型安全的数据模型，支持序列化、反序列化和验证。

### 决策

全面使用 Pydantic BaseModel 定义数据模型。

### 理由

1. **类型安全**: 运行时类型检查
2. **JSON Schema**: 自动生成 Schema 用于约束 LLM 输出
3. **序列化**: 内置 `model_dump_json()` 和 `model_validate_json()`
4. **生态**: 与 llama-index-workflows 深度集成

### 后果

- ✅ 减少手动验证代码
- ✅ 自动生成 JSON Schema
- ⚠️ Pydantic v2 的学习曲线

## ADR-007: 使用 Typer 作为 CLI 框架

### 状态: 已接受

### 背景

需要定义 CLI 命令，支持参数解析、类型校验和帮助生成。

### 决策

选择 Typer 作为 CLI 框架。

### 理由

1. **类型驱动**: 基于 Python 类型注解自动生成 CLI
2. **Rich 集成**: 与 Rich 库无缝集成，支持美观输出
3. **简单易用**: 比 argparse/click 更简洁的 API
4. **自动帮助**: 自动生成 --help 信息

### 后果

- ✅ 快速开发 CLI
- ✅ 类型安全的参数解析
- ⚠️ 复杂场景下灵活性不如 click
